## Short answer

- **The synthetic gate overstated acceptance and hid two defects.**
  - Real text accepts 4.4-5.3 tokens per full-draft round. The synthetic gate gave 6.81-6.88.
  - All 15 drafts are accepted in only 1.5-5.8% of rounds, so T32 stays rejected (the bar is 35%).
- **The real-text single-stream bar is 47.7 tok/s at 32k (v158) and 32.5 at 131k (v160).** Four
  users reach 19.8 (v157) and 17.2 (v159) per user in their packed rounds: 42% and 53% of the bar.
  The same flags on image A7 with T2 off (v184, v186) measure 21.0 and 20.7 (44% and 64%). At 131k
  the gap is v159's slow rounds, which v186 does not have (section 2, Rate).
- **At 4 x 131k only 29 of 134 decode steps are packed four-user rounds.** The rest run the 4-row
  sequential fallback, because real users finish at different times. The fallback, not the packed
  round, now sets the decode wall.
- **The four-user all-levers path is not byte-identical to single-stream on real text.** A bisect
  (v174-v178) finds one cause: `QWEN_FAST_SINGLE_GATEUP` (the C1/C1c prefill gate/up). Packing is
  exact, and every other lever is output-neutral on these prompts.
- **C1e fixes that exactly.** It rebuilds the served packed weight per layer into one 50.1 MB
  scratch and runs the unchanged fused op.
  - Card B: 0 mismatches against the served op, at +16.5 ms per 2048-row chunk.
  - The in-model arm is pending.
- **Wave 3 (`QWEN_FAST_VERIFY_T2`) is exact and takes 17.2 ms off the verify trace at both 32k and
  131k.** At 131k the packed round median falls only 10 ms (256 to 246), so the steady per-user
  rate moves only from 20.7 to 21.1 tok/s. The decode wall moves 0.2 s (40.3 to 40.1 s), because of
  the fallback: only 29 of the 134 decode steps are packed rounds.

## 1. Why real text

The synthetic gate prompt is token ids `base + i % 64` (bases 1000-1003), so it repeats every 64
tokens.
- Any window of the context predicts its own continuation, so the target's logits are peaked and
  the drafter is doing a copy task. The outputs repeat the same way: v163's streams are one 64-token
  cycle.
- On v146 (run 35919129565), none of the 132 per-user packed commits (33 rounds x 4 users) emitted
  11 or more tokens; the maximum was 10.
- vLLM's acceptance for draft positions 10-15 was 0.000, and the rejections fell on about 9-10 fixed
  cycle offsets (job file `architectural-levers-plan.md`, rank 4).

It hid three things:

1. **Acceptance.** The packed four-user arms at 4 x 131k commit 6.81-6.88 tokens per user per round
   on the synthetic prompt (the `[PACKED] emitted=` means of v148/v164). On real text they commit
   4.44-5.33 per full-draft round (section 2).
2. **The fallback for fewer than four users.** Four synthetic users accept at the same rate and
   finish in the same round, so the packed four-user round covered the whole decode. Real users
   accept 2.9-9.5 tokens per round, finish at different times, and spend most of the decode below
   four live users (section 2).
3. **A non-exact lever.** C1 passed 4/4 byte-exact checks over 256 tokens at 4 x 32k (v103, run
   35808667002) and 4 x 131k (v101, run 35809096034). The feasibility note says the unfused prefill
   "produces the same tokens as the fused one on these prompts". On real text C1 flips near-tie
   tokens (section 3). The periodic prompt's margins are too large to show a flip.

## 2. The real-text client (v157-v160)

**Corpus.** `real_text_prompts.py` builds the prompts inside the container, from the image's own
vLLM source.
- Source: `/opt/venv/lib/python3.10/site-packages/vllm`, 1,967 files, 27,103,228 characters,
  sha256 `6cf533fb`.
- 17 special-token strings are neutralised; for example `<think>` appears 57 times and `</think>`
  104 times.
- The corpus is split into four disjoint windows of about 6.78 M characters each. User u reads
  from the start of window u.

**Prompts.** Each prompt is a chat request with system prompt "You are a careful coding
assistant." The excerpt sits inside `<repository_context>`; the header warns that it may end partway
through a file. One of four long-output coding tasks follows:

| user | task | asks for |
|---|---|---|
| u0 | `pytest_tests` | pytest tests for the last complete function or class |
| u1 | `code_review` | a review of the last complete file |
| u2 | `explain_files` | a file-by-file explanation |
| u3 | `refactor_function` | a refactor of the last complete function |

**Length and budget.**
- Every prompt is exactly T tokens: 32,768 or 131,072.
  - The chat template takes 115-133 tokens.
  - Padding is at most 16 tokens of id 198; at most 1 was used.
  - The excerpts are 97-136 k characters at 32k and 435-573 k characters at 131k.
- EOS stop is on, and max_tokens is 256. That is the image's budget: the packed block admits only
  positions in the last 256 of max_model_len, so the context is T + 256 (33,024 or 131,328).
- Building the prompts takes 4.1-4.6 s at 32k (v157, v158) and 7.6-7.7 s at 131k (v160, v159).
- In v157-v160, every stream reached 256 tokens (`finish_reason` is `length`).

|---|---|---|---|---|---|
| v157 4 x 32k | 32 | 52 | 3 | 28 | 115 |

**Only the four-user steps run the packed 64-row block.** With 1-3 users alive, each user steps
through its own 4-row sequential verify engine, which emits at most 4 tokens a step.
- The count drops below four as soon as the fastest user finishes. At 131k that is u3, which
  accepts 9.5 tokens a round.
- The job's `variable-user-packed-round-plan.md` replays the v185 workload:
  - 1-3 live users plus the narrow transition take **84% of the decode wall**;
  - the packed rounds take 16%;
  - the per-user rate at 3 live users is 5.0 tok/s;
  - "today" is a 39.3 s decode wall, 13.5 tok/s mean completion rate per user, and 26.0 tok/s in
    aggregate.
- The same replay finds a second defect in the tail: pair users commit only 1.0-1.5 tokens per 4-row
  step, against 2.76-3.0 for single-proposal users in the same steps.

## 3. The exactness bisect

**v157 against v158 is NOT EXACT** (`real_text_compare`, all four streams at 256 tokens). The first
divergent characters are:
- at 32k (v157 vs v158): u0 80, u1 0, u2 758, u3 66;
- at 131k (v159 vs v160): u0 488, u1 1, u2 77, u3 206.

Every stream stays coherent; only near-tie tokens flip. u1 opens with "Looking" against "## Review"
at 32k, and "Let" against "Looking" at 131k.

**Ground-truth content check** (job file `realtext-divergence-2026-09-24.md`: the recorded prompt
tokens decoded with the served tokenizer, snapshot 1d4bf0f2). No arm loses its context tail.
- **32k u1.** The excerpt ends inside `fla/ops/kda.py`, and the last complete file is
  `fla/ops/index.py`. The reference reviews the cut `kda.py`; the packed arm reviews
  `fused_sigmoid_gating.py`. Both misread "last complete", in different ways.
- **32k u3.** The reference refactors the cut `maybe_make_thread_pool` and says itself that the file
  "appears to be cut off". The packed arm refactors `detokenize_incrementally`.
- **131k u1 (v159).** The packed arm names the cut method, `DeepGemmFP4Experts._act_mul_quant`, and
  the true last complete file, `cutlass_moe.py`. That is correct. The reference (v160) reviews the
  cut file.

The bisect arms were all at 32k on image A5 with K64g, 256 tokens unless stated. v174 is
single-stream (4 prompts sequential); the rest are 4 users packed:

| arm | run | change | compared with | result |
|---|---|---|---|---|
| v174 | 35947039218 | v158 + GDN prefill conv (single-stream) | v158 | **EXACT 4/4**: the prefill conv op is exact |
| v175 | 35947429760 | v157 - GDN prefill conv | v157 | **EXACT 4/4**: the lever set is deterministic, and the conv is cleared a second time |

| v177 | 35948139708 | the plain packed path (below) | v158 | **EXACT 4/4 over 256 tokens**: packing is exact |
| v178 | 35948591177 | v177 + `SINGLE_GATEUP` only | v157 | **EXACT 4/4**. It also diverges from v158 at the same characters (80 / 0 / 758 / 66) |

**The plain packed path (v177)** is v157 without `DRAFT_BF8`, `GDN_PREFILL_CONV`, `REPLAY_GROUP_ROWS`,
`ROUND_B1`, `SDPA_MODES`, `SDPA_PF`, `SINGLE_GATEUP`, `SKIP_BLOCK_STREAM` and `VERIFY_T1`. It keeps
`GDN_USER_BATCH`, the memory ledger and the 256 MiB trace region.

v177 exercised every packing mechanism that was under suspicion, and stayed exact:
- fresh ascending pages up to 2052;
- prefill slots 0-3, with GDN slot adoption;
- the startup trace captured before the first prefill;
- a different admission order: U0, U3, U1, U2.

**`SINGLE_GATEUP` is the only non-exact lever.** v177 = v158 shows that packing is exact. v178 = v157
shows that adding every other lever on top of `SINGLE_GATEUP` changes nothing. Later arms repeat the
result:
- at 32k, v183 and v184 (image A7, T2 on and off) are byte-identical to v157;
- at 131k, v185 and v186 are byte-identical to v159.

That makes the remaining one-lever arms (v179-v181) unnecessary for the conclusion.

**Why C1 cannot be exact.** The C1e analysis (`scripts/ci/mlp_c1e_pack.py`, `lever_n_m3native_patch`
section J) gives three reasons:
- **Double rounding of SwiGLU.** The served prefill MLP is
  `all_gather_minimal_matmul_async(fuse_swiglu=True)`. It forms silu(gate) * up from the fp32
  destination accumulators and rounds once to bf16.
  - C1/C1c rounds the SiLU'd w1 product and the w3 product to bf16 first, multiplies in bf16, and
    rounds again.
  - With the same fp32 gate and up, rounding first changes about 36% of products under
    round-to-nearest-even, and about 81% under truncation (`mlp_c1e_pack.py` docstring).
    `test_mlp_c1e_pack.DoubleRoundingTests` pins a share above 25% and the counterexample below.
  - For example, gate 0xbfb582d0 and up 0x3fad03bc give 0xbebf (-0.37305) fused and 0xbec0 (-0.375)
    separate.
- **K accumulation order.** C1c runs a different matmul program and K schedule: separate w1 and w3
  matmuls over 1024-row slices of x.
- **`packer_l1_acc`.** C1c runs the decode compute kernel config, which sets `packer_l1_acc=True`.

C1c's "EXACT" label meant bit-identical to C1, never to the fused path.

**Consequences.**
- 4 x 131k needs C1's 3.209 GB per chip; without it the run is about 1.9 GB per chip short (est.,
  divergence report). So the all-levers path at 131k cannot be compared with v160 until the prefill
  gate/up is exact, or until references are recorded under the same arithmetic.
- Until then, byte-exact gating against single-stream uses the v177 flag set at 32k.
- The divergence report's Part 1 recommends that `real_text_compare` report NOT COMPARABLE, rather
  than diverged, whenever the arms differ in an arithmetic flag.

## 4. C1e (`QWEN_FAST_C1_EXACT`)

**What it does.** C1e runs only under `SINGLE_GATEUP`, and is refused together with `C1_AGMM` or
`C1_LEGACY`.
- It allocates one scratch per chip (50.1 MB at TP2), built exactly as `_build_gate_up` builds
  `w_gate_up`.
- Before each layer's prefill MLP, one generic_op (`mlp_c1e_pack.pack_gate_up`) repacks that layer's
  w1/w3 into the scratch, in the fused tile order. It writes whole 576-byte bfloat4_b pages: packed
  page r*2C + 2c + g = (w1, w3)[g] page r*C + c.
- The unchanged served call, `tpc.all_gather_swiglu_prefill`, then reads the scratch.

The result has the same bytes, tensor spec, program config, compute kernel config, gather and
epilogue as the served path, so its output is the served output by construction. The cost per
layer per chip is 2 x 25.07 MB read and 50.14 MB written. For a correctness arm, `C1_EXACT_AUDIT=n`
byte-checks the premise at load and the first n packs.

**Card B**, image A5. The reports are `c1e-20260924T043849` (the watcher pass) and
`c1e-20260924T043926` (the full pass), from `optimisation/ttnn-op/c1e_gateup/c1e_gateup_card_b.py`.
- The harness uses random weights of the real TP2 per-chip shapes: w1/w3 [5120, 8704] and the packed
  [5120, 17408], all bfloat4_b.
- It runs single-chip `minimal_matmul`, because card B has no Ethernet.

| check | result |
|---|---|
| C1e against the served op, raw bf16 bits: 128 / 256 / 512 / 1024 / 1056 / 1536 / 2048 rows, both chips' shapes, 2 seeds (28 cases; the watcher pass ran 2048 and 1056 rows, chip 0, seed 0) | **0 mismatches** in every case; the served op rerun is also 0 in all 28 |
| C1c control on the same cases (expected to differ) | 0.40-6.51 M mismatched elements per case, about 36% of the elements (3.35-6.51 M at 1056-2048 rows); max ulp 13-15, and 1924 on chip 1 seed 1. So the harness can see the divergence v178 saw |
| pack bytes (`packed_weight_check.cpp`, 43,520 pages per tensor, both chips) | the served packed tensor and the scratch are both byte-equal to the w1/w3 interleave, with equal tensor specs |
| repeated packs; negative controls | no new program-cache entry; a packed weight from other random weights differs in 17.8 M of 17.8 M elements, so the checks can fail |
| timing at 2048 rows (median, 20 iterations) | pack 0.32 ms per layer alone, 0.257 ms pipelined back to back (389.5 GB/s over 100.3 MB); fused op 1.76 ms, against 2.05 ms for C1c |
| penalty against the resident served weight, per 2048-row chunk (64 layers) | **C1e 16.5 ms** (64 x the pipelined pack); C1c 18.2 ms (64 x (2.05 - 1.76), gate/up only) |

**For one 131k prompt** (64 chunks):
- C1e adds about 1.05 s and C1c about 1.16 s against the fused path (est.).
- C1e keeps about 3.16 GB per chip of C1's 3.209 GB saving (est.).

**The in-model arm is pending.** The prediction, which rests on v178 = v157 above:
- v157's flags + `C1_EXACT` are byte-identical to v158 at 32k;
- v159's flags + `C1_EXACT` are byte-identical to v160 at 131k.

That would give the 4 x 131k configuration both the fit and single-stream exactness.

## 5. Wave 3 (`QWEN_FAST_VERIFY_T2`) validation

Contract: job file `verify-t2-contract.md`; commits 92699523 and 6a83e076. Wave 3 makes two cuts:
- **#1, packed GDN conv windows.** 192 window launches per replay become 48: one 110-core byte copy
  per GDN layer, reading the per-user pieces.
- **#2, chained ordered K/V write.** 64 launches plus 64 slices become 32 launches: one chain per
  user, using the hash-pinned `ordered_cache` kernels. A per-round host guard sends any round with a
  tile conflict down the sequential step.

The contract estimated -14 ms (-13.6 to -17.5) on the 157.4 ms trace.

**Card B** (`vt2-20260924T012904`):
- The packed windows launch (`hist1_noc1_nbuf1`) takes 37.6 us. It replaces four served launches,
  296.2 us together on card B (72.30 us each in the v138 profile, about 289 us per GDN layer).
- The K/V write takes 58.9 us per call chained (`chained64`), against 219.2 us served.
- The default setting came from the earlier `vt2-20260924T012053`, run on commit 92699523. There,
  the previous default `hist1_noc0_nbuf2` took 62.5 us and the literal port 105.9 us. Commit
  6a83e076 then made `hist1_noc1_nbuf1` the default, and `vt2-20260924T012904` passed on it.

**v169: a false alarm from the audit.** v169 (run 35944240281, image A6, 4 x 32k synthetic, T2 plus
its audit) died on its first packed round:
`[PINDIAG] verify t2 audit mismatch round=1 layers=0-47 layer 0 user 0 slot 0 chip 0: 76673`.
- The packed windows were right; the audit was wrong.
- `gdn_decode_conv_gates` shifts its window inputs in place (slot 1->0, 2->1, 3->2, x->3), and only the
  packed windows had gone through it. So the audit compared shifted packed windows with unshifted
  served ones: every row was one out.
- The fix, 8d078e11 (image A7), sends the served reference windows through the same conv-gates call
  under the audit. The audit-off path is unchanged.

**v182: the audit is exact.** v182 (run 35949113912, image A7, v169's config) ran 34 audited rounds,
all exact. Round 1 covered all 48 layers (768 windows), and every later round covered 2 layers. All
4 users are identical to the synthetic 256-token references. This is a correctness arm; its trace is
not a timing.

## 7. Roofline headline

Source: job file `roofline-4x131k-2026-09-24.md`. It is analysis only, uses synthetic acceptance,
and predates wave 3.

**Decode round:**
- **Today's 4 x 131k round is 240-242.5 ms** (v148/v146; v164's 261 ms is host noise).
- **It uses about 23-25% of the pair's DRAM roofline.**
  - The idealised roofline is 59.3-60.6 ms per round: 22.46 GB per chip per round, with bf8 at
    390 GB/s and bf4 at its measured 286-324 GB/s.
  - The serial per-op floor is **69-96 ms (est.)**, so today's round is 2.5-3.8x above it.
- **The device idles 36-57 ms per round on host fences.** Its ~204 ms of busy time moves ~27.7 GB
  per chip, about 135 GB/s, or 35% of 390 (est.).
