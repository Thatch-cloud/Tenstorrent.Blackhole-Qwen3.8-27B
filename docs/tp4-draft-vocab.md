# tp4/draft-vocab: the DFlash2 drafter proposes from a coding shortlist of the vocabulary (`QWEN_FAST_DRAFT_VOCAB`)

Status: built and tested on CPU (`test_draft_vocab_tp`, `test_draft_vocab_build`, `test_tp4_draft_vocab_jobs`); **nothing here has run on a card**. Default off, gate only, byte-identical off
(`QWEN_FAST_DRAFT_VOCAB` unset, empty or `0`: no module is imported and every function it touches is the body it always was). Every figure in section 5 is an **ESTIMATE**.

## 1. What it does, and why the text cannot change

The target verifies every proposal over the full 248,320-row vocabulary with its own weights. This lever never touches the target's head, its sampler or its verify; it only restricts which tokens the
drafter can **propose**. A token outside the list can never be proposed, so a round that needed one is cut short there: the cost is accepted length (tau), never correctness. Committed text is the target's
own greedy decode whatever the list holds; the timing pack still compares the texts (`levern_compare.py`, every answer's hashes equal) because "by construction" is not "measured".

## 2. What the drafter's head costs today

The DFlash2 drafter has no vocabulary head of its own. Its head is the **target's** LM head run on the draft rows (`draft_shared_head_tp.shared_head_candidates`, which the single-user pass, the pair
and the quad/octo passes all call):

| Per chip, TP4 | Today | With the shortlist |
|---|---|---|
| head weight read per call (5,120 rows) | 62,080 columns: 317.8 M elements, 337.7 MB in bfloat8_b (635.7 MB if the head were bfloat16) | 10,240 columns: 52.4 M elements, 55.7 MB (104.9 MB) |
| logits written per call (32 rows) | 4.0 MB | 0.66 MB |
| top-16 launches per call | 2 (32,768 columns, then the 29,312 left padded with -inf to 32,768) plus two slices | 1 (10,240 columns padded with -inf to 32,768, the width every drafter top-16 has run at; 16,384 is the second arm) |
| candidates read back per call (values + indices, each chip) | 2 chunks x 2 = 4 reads | 1 chunk x 2 = 2 reads |
| columns the head cannot propose | 0 | 207,360 of the 248,320 (the padding rows 248,077 and up are not tokens at all) |

The head runs once per 32-row half of a pass (`quad_draft_tp.head_candidates`): **two calls per quad or octo pass**. An eight-live round of the production shape drafts with two quad passes
(`QWEN_FAST_QUAD_DRAFT_BLOCKS=2`), so it makes **four head matmuls, eight top-16 launches and 36 readback reads** (2 x 18) today, and four, four and 20 with the shortlist.
The dtype of the target head is not asserted anywhere in this repository's served code; `tp4_profile_report.weight_table` assumes bfloat8_b and so does the arithmetic above. `build_head` reads the real
dtype from the tensor, uploads the slice in it and logs it (`dtype=` and `bytes_per_chip=` on the `head built` line).

The selector is not on the device: `select_active_candidates` runs on the host in FP64 over at most 16 candidates per row, and its two codebooks (vocabulary x 256, indexed by **global** token id) are
gathered only at those candidates' ids. So nothing about the codebooks needs slicing: candidates are mapped back to global ids before the selector sees them.

## 3. The shortlist

`scripts/ci/draft_vocab_coding_40960.ids` (uint32 little endian, ascending global ids, 163,840 bytes) with its statistics in `draft_vocab_coding_40960.json` (sha256 of the list, the 289 required ids,
the corpus counts, the coverage curve). Generated by `scripts/ci/draft_vocab_build.py` (stdlib for the pure parts; `tokenizers`, `pyarrow` and `numpy` for the command line). Rows are a multiple of 128
(four chips x one 32-row tile).

**Corpus (public text only; no model was run, no customer or own-session text was read).** Token frequencies of text shaped like a coding agent's output, rendered deterministically from:
the gold patches of the public SWE-rebench dataset (CC-BY-4.0; 13,713 instances) as `str_replace` / `create` tool calls in the served chat template's markup (`edit`), its test patches the same way
(`test`), its issue statements and maintainer hints wrapped as thinking (`prose`), bash tool calls built from its test ids, paths and identifiers (`shell`), and open-source source files found on
the building host (Python x 1,501 files, Rust 1,069, JavaScript/TypeScript 943, C/C++ 5,207) sampled by path hash up to a byte budget. Each category is counted alone and mixed with fixed weights
(edit 0.30, test 0.10, prose 0.25, shell 0.05, python 0.10, rust 0.06, js 0.06, c 0.08) so a category's size does not decide its weight. One document in ten (by repository, or by path) is **held out**
and never counted for selection; every coverage figure below is the held-out one.

**Always kept:** all 33 added tokens of the tokenizer (chat, vision, FIM, `<tool_call>`, `</tool_call>`, `<tool_response>`, `<think>`, `</think>`, `<|im_end|>`, `<|endoftext|>`, ...; ids 248,044 to 248,076)
and all 256 single-byte tokens (the byte alphabet: any text is spellable). 289 of the 40,960 rows are these; the other 40,671 are the most frequent by the mixture, ties to the lower id.

**Coverage of held-out tokens (fraction of occurrences whose token is in the list):**

At 40,960 rows: edit 0.9888, test 0.9900, prose 0.9910, shell 0.9970, Python 0.9946, Rust 0.9965, JS/TS 0.9938, C/C++ 0.9937 (all above the 0.96 bar; the stated target). The curve says the bar is met from about
20,480 rows, so a smaller list (a head 2x cheaper again, tau a little lower) is a rerun of the generator with `--rows 24576`, not a code change; it is the follow-up if the first ABAB is positive.

**What the coverage is not.** It is a proxy: the frequency of tokens in public coding text, not in this model's own output, and the corpus is Python-heavy (SWE-rebench is Python; other languages
come from whatever sits on the building host). The tau lab's `dvocab` arm on the model's own thinking-ON output is the measurement that counts. The tau lab's A1 turns are drawn from the same public
dataset; the list was built from repositories that hash into 9 of 10 buckets and the lab's 240 turns may include some, which can only flatter A1 by a hair (a frequency list does not memorise turns), and
A2 (the scrubbed own sessions) is untouched by construction.

## 4. How it works

* **Flag** `QWEN_FAST_DRAFT_VOCAB=<name or absolute path>` (strict; a name is `coding-40960`, pinned by sha256 in `draft_vocab_tp.NAMED`; a path is an id list the generator wrote). `QWEN_FAST_DRAFT_VOCAB_TOPK`
  = `32768` (default) or `16384` (needs the flag; the narrower launch is a shape no card has run). Four cards only (`QWEN_FAST_TP=4`): the pair's `draft_shared_head` is sha-pinned and is never edited.
* **Attach** (`serving_runtime.attach_combined_runtime`): the flag is admitted (or refused by name) before anything is built; after the shared draft weights and before any trace is captured, `build_head`
  reads each chip's shard of the target head back, picks the list's columns on the host (one shard in memory at a time), and uploads them in the head's own dtype, sharded on the vocabulary axis, **evenly**:
  chip c holds the c-th quarter of the list in id order (10,240 columns), however lopsided the natural shards are (32,558 of the 40,960 ids sit in chip 0's natural shard). A buffer
  allocated after a trace was captured can sit in that trace's freed holes (the account at `PreparedDraftWeights`), which is why the build is an attach step and never a request step.
* **Head** (`draft_shared_head_tp`, four functions guarded by `vocab_requested()`): one `linear` over the sliced weight, the logits padded with -inf to the launch width, one top-16, **one chunk per chip**
  `(0, 10240)`. `candidate_chunks()` follows, so the pooled draft output buffers (`pooled_draft_output_shapes`), the quad/octo readbacks and the round-host batched merge all see one chunk.
* **Mapping and selection** (`draft_vocab_tp.merge_chunk_candidates`, and `round_host._fast_merge`): a chip's local index becomes `ids[chip * 10240 + start + index]`, the **global** token id, before the
  merge sorts by token id (stable) and then by score (stable, descending). Ties therefore go to the lowest global id exactly as in the full-vocabulary merge (the list is ascending and the chips hold it in
  order). The FP64 selector, its codebooks, the anchors and every downstream consumer are today's code on today's kind of operands. When the full vocabulary's top-16 lies inside the list the candidates, their
  scores and the proposals are identical (`test_draft_vocab_tp.SelectionEquivalenceTests`); when it does not, every candidate is inside the list and is the top-16 of the logits restricted to it.
* **Precision.** In a block-float dtype the regrouped columns share exponents differently from the target head's, so a shortlist logit can differ from the target head's in the last mantissa bits (bfloat16
  would be exact). That moves proposals only, and the paired timing read's tau is where it would show.
* **Markers** (`c2_smoke_check.draft_vocab_problems`): `[PINDIAG] draft vocab admitted ...` once at the attach, `... head built ... dtype= bytes_per_chip=` once, `... engaged ...` once at the first head
  launch, all naming the same rows; flag off, **no** such line. There is no fallback: a failure raises.
* **Contract.** An unknown `QWEN_FAST_DRAFT_VOCAB*` name, a width flag without the list, a list the four-card head cannot serve, the pair, or a profile that is neither gate-only nor the tau lab's
  `<base>+taulab+dvocab` is refused at boot; an inherited process value is dropped from a profile that does not name it (`serving_c2_contract.draft_vocab_problems`, `apply_environment`).
* **Memory.** About 56 MB a chip (bfloat8_b; 105 MB in bfloat16) of DRAM, one copy shared by every pass. The eight-seat x 262k pool sits at 19,968 of 19,979 blocks, so the timing twins give the pool back
  (19,712 blocks, 142.6 MB, `QWEN36_MAX_TOKENS_ALL_USERS` 1,261,056) and **both** carry the smaller pool so the ABAB differs in the lever alone (`make_dvocab_profiles.py`).

## 5. ESTIMATE of what it saves per eight-live round

Basis: an eight-live round of the production shape drafts with two quad passes (docs/tp4-batched-draft.md, tp4-octo-draft.md); the O3 card run measured that shape's cycle at **159.5 ms** (verify and commits
112.9 ms, gap 46.6 ms of which the early draft is about 43 ms). Per round the lever removes four head matmuls' worth of weight streaming, four top-16 launches, their slices and 16 of 36 reads.

| Term | Reasoning | Per round |
|---|---|---|
| Head matmul weights | 4 calls x (337.7 - 55.7) MB = 1,128 MB at 420 GB/s achieved (512 peak; docs/tp4-drafter-bf16.md) down to 230 GB/s (the tile-rate-bound figure docs/tp4-profile.md measured for bf4 gate/up). M = 32 rows is weight-bound. | **2.7 to 4.9 ms** (central 3.6) |
| Top-16 launches, slices and pad | 4 fewer top-16 launches of 32 x 32,768, 8 fewer slices/pads of up to 4 MB. **No top-16 timing exists in this repository**; 0.1 to 0.3 ms per launch is a guess. | **0.4 to 1.6 ms** (central 1.0) |
| Readback | 16 fewer small reads at 0.1 to 0.25 ms (octo-draft doc: `collect_ms` 4.6 for 18 reads); part may overlap the device tail. | **0.8 to 4 ms** (central 2.4) |
| **Total** | | **about 6 ms, range 3 to 10 ms** |

About 6 ms is **3.8% of the 159.5 ms cycle (range 1.9 to 6.3%)** and 13% of the draft phase, before any tau change. If the target head were bfloat16 the matmul term roughly doubles. If the draft phase is
host-bound rather than device-bound the saving shrinks toward the bottom of the range (the octo-draft doc bounds the draft phase at about 18 ms of hidden host work), and the readback term is the likeliest
to be absorbed. **The break-even tau loss is therefore about 4% (2 to 6%).** The expected tau cost is well under that: a rejection from the list needs the target's next token to lie outside it
(0.9% of held-out code tokens, 1.0% of prose) and the drafter to have proposed it right (it is rarely right on rare tokens), over about four accepted positions: **an estimated tau cost of 0.5 to 1.5%**. Net
**+2 to +3% committed tokens per second per seat, with a tail where it is negative**. The two measurements that replace this paragraph are the tau lab's pooled ratio (D-V2) and the early draft median
of the ABAB (TV1 to TV4). It is not a path to the 75 tokens per second target by itself.

## 6. Tests (CPU)

`test_draft_vocab_tp` (64): the committed list (pinned, ascending, every special and single-byte token, four whole tiles, no padding row), strict flags, list validation, the mapping and the merge (any arrival order,
ties to the lowest global id, a malformed readback), the round-host batched merge bit for bit, selection equivalence through the real FP64 selector, the op sequence on a fake ttnn (the sliced weight, one padded
top-16, one chunk, the 16,384 launch, input checks), the build of the sliced weight from fake shards (columns, chip order, dtype, mesh mapper, bytes), flag-off identity (the twin imports nothing, the full-vocabulary
merge is unchanged), the contract, the smoke rule and the three image copy lists. `test_draft_vocab_build` (23): required tokens, selection, mixture, coverage, the rendering of public text, the committed list and
its sidecar (sha256, coverage, hygiene). `test_tp4_draft_vocab_jobs`: the timing twins, the lab's arm, the noninferiority bar, the paired timing read and the job pack.

## 7. Cards: `scripts/ci/references/tp4-draft-vocab-jobs`

`B0` build, `X0` status/rescan/reset, **`S1` the smallest safe step** (the timed arm's profile booted once with warmup, the steady eight-user shape and one coding answer: the head uploads inside the pool
given back, the shapes compile in the parked traces, the markers show; 30 minutes), `D-V1` the control tau arm and `D-V2` the **`dvocab`** tau arm (same image, `drafter_pair_report.py`, noninferiority at 0.97),
and the **ABAB** `TV1` (control), `TV2` (arm), `TV3`, `TV4` at eight live with CI paused, read with

    python3 scripts/ci/draft_vocab_report.py --control <TV1 container log> <TV3 container log> --arm <TV2 container log> <TV4 container log> --live 8
    python3 scripts/ci/levern_compare.py --control <TV1 smoke log> --levern <TV2 smoke log>      # and TV3 against TV4: exit 0

The report prints, per pair, the early draft median at eight live (the number the lever is for), tau, round time and the per-user rate over the paired rounds, and its pre-registered verdict: GO needs every pair
at +2% on the per-user rate with a lower early draft median and tau not under 0.97 of the control's; NO-GO is a rate under the control's or tau under 0.95; MAYBE in between; UNREAD with under 100 paired rounds
or 30 early drafts. Every result is UNQUALIFIED.

## 8. Not done, and the risks

* No card has run any of it. The first card question is S1: does `from_torch` accept the 10,240-column bfloat8_b slice sharded on dim 3, does the auto `linear` program accept the narrower N, does the top-16
  accept a 10,240-wide input padded to 32,768 inside a captured trace. The arithmetic in section 5 assumes all three.
* The pool is given back by 256 blocks for both timing twins; the production profile is not changed. A shortlist in production needs the same pool arithmetic in its own profile.
* The 16,384-wide launch (half the top-16 work) is an arm of its own, behind `QWEN_FAST_DRAFT_VOCAB_TOPK`; no job runs it.
* A 24,576-row list reaches 97.3% held-out coverage and would roughly halve the matmul term again; it is not committed because the first measurement should be the stated 40,960.
* Eight-seat quad blocks are the shape timed; the single-user pass (the tau lab) and the pair pass call the same head and are covered by the same tests, not by a timing arm.
* The parked draft traces bake the sliced weight's address: the head must live as long as the process (it is freed with the attach scope, after the traces).
