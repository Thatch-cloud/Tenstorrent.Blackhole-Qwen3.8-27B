# T16-vs-B1 mismatch at 65536 (run 35615160970, `frozen-64k-target-replay-scratch-v8`)

## 1. What the assertion actually compares

`target-t16-attention-8k-probe.py` is rewritten in place by
`frozen_target_replay.adapt_target_probe` before it runs
(`scripts/ci/frozen_target_replay.py:68-132`), so the failing assertion is
**not** the file's own original comparison. The patch:

- Inserts a `ReplayAttentionReader` (T16) call *before* the native-reference
  loop even starts, capturing its output as `allocation_host`
  (`frozen_target_replay.py:87-95`, prints `stage=target-allocation-ready`).
- Replaces the original try/finally `torch.equal(host(warm), gold[0])` check
  with a bare `torch.equal(allocation_host, gold[0])`
  (`frozen_target_replay.py:102-110`). Exact equality, no tolerance.

Both sides are query position **65536** (`starts[0] == first == capacity-256`,
`target-t16-attention-8k-probe.py:53-54`), same `initial` query tensor.

- **"native B1"** = `gold[0]`, built by the untouched loop at
  `target-t16-attention-8k-probe.py:68-82`: 16 separate calls to
  `ttnn.transformer.paged_scaled_dot_product_attention_decode`, one query
  **row** at a time (`row_query = ticket_query[:, row:row+1]`), each with its
  own `cur_pos_tensor`, `program_config` = `q_chunk_size=0, k_chunk_size=0`
  (`:37-38`), **no** `attn_mask`, **no** `is_causal` kwarg (API default,
  internal causal masking from `cur_pos_tensor`) — line 75-77.
- **"T16"** = `allocation_host`, from `ReplayAttentionReader.__call__`
  (`attention_replay.py:118-141`) → `attention_parallel.execute`
  (`attention_parallel.py:6-30`): all 16 rows folded into ≤4-row groups
  (`max_group_rows=4` default — the reader is constructed without an
  explicit override, `frozen_target_replay.py:87`), one device call per
  group with an **explicit dense bf16 `attn_mask`** (`is_causal=False`,
  `attention_parallel.py:17-19`) built host-side by
  `attention_head_fold.causal_mask` (0/-inf over the **full capacity width**,
  not chunk width — `attention_head_fold.py:19-28`), `program_config`
  `q_chunk_size=0, k_chunk_size=256` (`attention_replay.py:53-54`) —
  **patched at 65536 only** to read
  `QWEN_FROZEN_65536_REPLAY_K_CHUNK` (default **128**,
  `frozen_wide_chunk_replay.py:56-77`; this run's `frozen-geometry.json`
  confirms `attention_replay.py` is in the staged/patched set).

**Both sides call the same op**, `paged_scaled_dot_product_attention_decode`,
which dispatches to `sdpa_decode_program_factory.cpp`. Neither side calls
`scaled_dot_product_attention` (the non-decode op). Tolerance is
`torch.equal` (bit-exact), not `isclose` — no slack anywhere in this check.

## 2. What the artifact says about magnitude — and what it doesn't

`target-t16-attention-8k.json` (from `gh run download 35615160970`):

- `checks: []`, `mask_checks: []`, `source_checks: []`, `stale_controls: 0` —
  every field the *later*, diagnostic-rich per-ticket loop
  (`target-t16-attention-8k-probe.py:117-138`, which populates a `failure`
  dict with `max_abs`, `mismatches`, `nonfinite`, `mask_exact`) would have
  filled in is empty. That loop is **never reached**: the process crashes at
  the earlier, patched bare-`torch.equal` check
  (`frozen_target_replay.py:109-110`), which has **no diagnostic capture at
  all** — it either passes or raises, with zero element-wise data.
- `simulator-container.log` and the workflow log contain nothing past the
  traceback (`AssertionError: T16 long-context warm output differs from
  native B1`, `target-t16-attention-8k-probe.py:110` post-patch) — no printed
  tensor stats.
- Timing: `target-allocation-ready` (T16 side computed) at 15:47:29, three
  `native-reference` stages (B1 rows, ~2m20s-2m30s each) through 15:54:44,
  then immediate failure. 724s total (`probe-timing.json`).

**Conclusion: there is no max-abs, no element/row/head count, no
finite/NaN breakdown available from this run.** The comparison that failed
is structurally incapable of producing that data — it was rewired
(§1) into a blunt boolean specifically to reuse the T16 output computed at
`target-allocation-ready` instead of re-running `reader(...)` a second time,
and diagnostics were never added back. Getting magnitude/pattern data
requires either (a) a rerun with the *original*, un-rewired
warm/gold comparison restored (accepting the extra `reader()` call this
patch was designed to avoid), or (b) a one-off script that loads
`allocation_host`/`gold[0]` — but neither is captured or persisted anywhere
today, so a rerun is unavoidable either way. **This cannot be classified as
"same bf16 signature" vs "structural" from evidence in hand.**

## 3. Do the four precision fixes apply to this kernel? No.

`frozen_wide_chunk_normalization.py` (commit `31c3d891`, "the full ladder
precision set") patches `dspark_fp32_intermediates.py`, whose `SOURCE` is
`ttnn/cpp/ttnn/operations/transformer/sdpa/device/sdpa_program_factory.cpp`
(`dspark_fp32_intermediates.py:6-18`) — the **prefill-style** SDPA factory
behind `ttnn.transformer.scaled_dot_product_attention`, gated by
`qwen_draft_fp32_intermediates = B==1 && NQH==16 && ... && !is_causal &&
compute_use_provided_mask && !is_chunked && ... && fp32_dest_acc_en &&
!exp_approx_mode` plus a `Skt` branch (2112 by default,
`frozen_wide_chunk_normalization.py:92-114`). The other two fixes
(`frozen_wide_chunk_sum_update.py`, `frozen_wide_chunk_score_center.py`) are
parameterized ports gated the same way, on the same file family.

The target-replay path (§1) never calls that op. Its own docstring says so
explicitly: `frozen_wide_chunk_normalization.py:296-305` — *"`sdpa_tree_scratch.py`'s
own pins... are entirely about... `sdpa_decode_program_factory.cpp` — the
DECODE kernel family `attention_replay.py`'s `ReplayAttentionReader` actually
computes through... a completely different file from
`sdpa_program_factory.cpp`... The compact-scratch target probe's own numerics
and scratch CB layout... are therefore not coupled to
`sdpa_program_factory.cpp` at all."* `docs/numerics-65536-attention.md:470-480`
makes the identical statement. This run's own artifact confirms it built and
audited *both* factories (`target-t16-attention-8k.json.factory_build` — the
`sdpa_program_factory.cpp` rebuild, redirected through
`frozen_wide_chunk_scratch.validate_manifest` per
`frozen_wide_chunk_normalization.py:275-307` — plus `native_sources` /
`native_sources_after` pinning `sdpa_decode_program_factory.cpp` via
`sdpa_tree_scratch.HASHES`/`PATCHED_FACTORY_SHA256`,
`sdpa_tree_scratch.py:7-13,16-23`), but the `factory_build` entry is pure
build-provenance audit of a binary neither side of the T16-vs-B1 comparison
depends on.

**`sdpa_decode_program_factory.cpp` — the file both sides actually run
through — has no Skt branch and no fp32-intermediate substitution of its
own in this repo's staging.** The only patch it receives at all is the
"compact scratch" candidate pinned by `sdpa_tree_scratch.py` (a tree-reduction
scratch-buffer layout for `QWEN_SDPA_TREE_SCRATCH_ROUNDS=1`/`max_group_rows=8`
grouped calls — `sdpa_tree_scratch.scratch_slots`,
`sdpa_tree_scratch.py:26-29`), which is a workers/scratch-slot layout change,
not a precision fix, and is unconditionally active on *both* the T16 and B1
sides here (same binary, same hash, for every call) since it's a global
`sdpa_decode` build. It is also active, unchanged, at the passing 32768 lane
(scratch-v4) — so it alone does not distinguish pass from fail.

**What actually changes between the passing 32768 lane and this failing
65536 lane, on the decode path itself:**
1. Capacity roughly doubles (33024 → 65792), so both the T16 masked-chunk
   softmax (more `k_chunk_size` merge steps) and the B1 auto-chunked path
   accumulate over ~2x more keys.
2. T16's `k_chunk_size` changes from the **hardcoded 256**
   (`attention_replay.py:54`, untouched at every other context) to a
   **65536-only override, default 128**
   (`frozen_wide_chunk_replay.py:56-77` — commit `43a1da0d`, *unrelated* to
   the precision-fix commits; it was introduced to fix a build-time L1 CB
   overflow, run 35585801822, not a numerics bug — its own docstring
   (`frozen_wide_chunk_replay.py:18-27`) says the CB-overflow cause is more
   likely the dense full-capacity mask buffer than chunk width, and calls
   the knob "a diagnostic as much as a candidate fix"). B1's `k_chunk_size=0`
   is unchanged at every context.
3. `max_group_rows` stays at its default (4) at both contexts — no evidence
   the fold width itself changed.

A `256`-vs-`0` k_chunk mismatch between T16 and B1 already exists at 32768
and produces bit-exact agreement there, so a T16/B1 chunk-width mismatch is
not new. What's new at 65536 is a *narrower* T16 chunk (128, half of what
worked at 32768) layered on ~2x more accumulation, in a build that has never
previously reached this specific comparison (every prior 65536 attempt died
earlier — a factory-pin bug through v6/v7, `docs/numerics-65536-attention.md`
§8 — so there's no earlier 65536 data point with a *different* k_chunk value
to compare against).

## 4. Ranked candidate fixes and the cheapest diagnostic

1. **(Cheapest, do this first) Rerun with
   `QWEN_FROZEN_65536_REPLAY_K_CHUNK=256`** (the documented "unchanged
   control", `frozen_wide_chunk_replay.py:6-7`) as an A/B against this v8
   result. Same lane, one env var, no code change, no rebuild (the knob is a
   runtime `SDPAProgramConfig` field, not a compile-time one — confirm via
   `attention_replay.py:70-75` post-patch). If it passes: k_chunk=128 is
   implicated, and the CB-overflow motivation for narrowing it
   (`frozen_wide_chunk_replay.py`'s own docstring) needs a different, cheaper
   fix (e.g. shrink the dense mask buffer instead, per its own CAVEAT) rather
   than accepting a numerics regression. If it still fails: capacity/scratch
   depth, not chunk width, is the driver — go to (2).
   **Risk: low. Requalification cost: one ~12-minute CI run** (same as this
   one, since it must still walk the native-reference loop).
2. **Restore diagnostics**: temporarily skip
   `frozen_target_replay.adapt_target_probe`'s early-exit rewiring (or patch
   in a `max_abs`/`mismatches`/`nonfinite` capture at the failing
   `torch.equal` in `frozen_target_replay.py:109-110`) so the next failure
   actually reports magnitude and shape — needed regardless of which
   hypothesis below is right, since nothing here can currently distinguish
   "2-ulp bf16 rounding" from "wrong rows". **Risk: low (diagnostics only,
   same run cost). Requalification: none — informational.**
3. **Compact-scratch tree-depth scaling**: `sdpa_tree_scratch.scratch_slots`
   is a function of `workers` (`sdpa_tree_scratch.py:26-29`); if the K-chunk
   (reduction-tree worker) count the pinned patch was sized for assumes
   something closer to 32768's capacity, ~2x more chunks at 65536 could
   silently under-allocate scratch and corrupt partial sums — *structural*
   (specific rows/chunks wrong), not a smooth bf16 gradient, in whatever
   diagnostic (2) produces. Needs the patched
   `sdpa_decode_program_factory.cpp`/`sdpa_flash_decode.cpp` source from the
   pinned `tt-metal` checkout (not present in this repo) — flag as the next
   thing to pull. **Risk: medium (kernel change). Requalification: full
   rebuild + both 32768 and 65536 lanes.**
4. **Explicit dense `attn_mask` vs internal `is_causal`**: T16 adds a
   bf16 0/-inf mask (`attention_head_fold.py:19-28`) to raw scores; B1 relies
   on the op's own `cur_pos_tensor`-driven masking with no such tensor. These
   are different mechanisms and could round differently right at the
   boundary tile, but this mechanism is unchanged between 32768 (passing)
   and 65536 (failing), so it is a weaker candidate than (1)/(3) unless (1)'s
   control still fails. **Risk: low to investigate (no code change, just
   inspect the boundary tile in whatever diagnostic (2) produces), high to
   fix (would mean reconciling two different masking code paths).**

Recommended order: run (1) immediately — a single env var splits "new
65536-only knob" from "capacity-scaling problem inherent to the qualified
32768 design." Land (2) in parallel so the next failure, if any, comes with
real numbers instead of a bare boolean.

## RESOLVED 2026-09-22 — it was the gate, not the kernel

Run `35662960713` (k_chunk 128, the documented default) carried the diagnostics this document
asked for in its section 4.2, and they settle the question on the first attempt:

```json
{"stage": "t16-b1-mismatch", "tensor": 0, "start": 65536, "shape": [1, 16, 12, 256],
 "elements": 49152, "mismatching": 43266, "max_abs": 3.0517578125e-05,
 "mean_abs": 4.563241873256629e-06, "nonfinite": 0, "rows_affected": 192,
 "first_rows": [0, 1, 2, 3, 4, 5, 6, 7]}
```

`max_abs` is **3.0517578125e-05 = 2⁻¹⁵ exactly** — a power of two to the last bit, which is what
one bf16 ulp looks like for values in [2⁻⁸, 2⁻⁷). Read with the rest:

| signal | value | what it eliminates |
|---|---|---|
| `max_abs` exactly 2⁻¹⁵ | 1 ulp | accumulated error — that does not land on a round power of two |
| `mean_abs` 4.56e-06 | ~0.15 ulp | systematic bias |
| `nonfinite` 0 | none | overflow, uninitialised scratch, bad addressing |
| `rows_affected` 192 of 192 | all rows, uniformly | wrong-rows and chunk-boundary bugs, which hit a *subset* |
| `mismatching` 43266 / 49152 | 88% of elements, each ≤1 ulp | anything with magnitude |

This is the fingerprint of two mathematically identical computations rounding differently in
bf16 because they merge in a different order — precisely what a different `k_chunk_size`
produces, since it changes the online-softmax merge sequence. B1 runs `k_chunk_size=0`, T16 runs
128.

**So the comparison was never a numerical statement.** `torch.equal` between two differently
ordered bf16 reductions cannot succeed, and a check that cannot succeed distinguishes nothing.
It was not detecting a defect; it was reporting its own premise.

### What this retires

- **Candidate 3, compact-scratch tree-depth scaling**, predicted *structural* damage: "specific
  rows/chunks wrong, not a smooth bf16 gradient". The gradient is smooth and universal, so the
  hypothesis is dead — without needing the pinned `sdpa_decode_program_factory.cpp` this document
  flagged as "the next thing to pull".
- **Candidate 1's decision value.** The k_chunk 256 control still distinguishes chunk width from
  capacity scaling, but it is now a confirmation that rounding is the mechanism, not a test of
  whether something is broken.
- **The four staged precision fixes** were already ruled out in section 3 (they patch
  `sdpa_program_factory.cpp`, the prefill op neither side calls). Nothing here revives them.

### What replaced the gate

The comparison is now an **ulp budget** rather than a bit-exact equality
(`frozen_target_replay.py`, staged into the probe):

- Shape and dtype stay exact — the budget is for values only.
- Every element's difference is measured in ulp of the B1 reference, floored at 2⁻¹⁶ of the
  tensor's own maximum magnitude so near-zero entries are not compared relatively.
- `MAX_ULP = 4.0`: four times the measured worst case, and still more than an order of magnitude
  below anything structural. A single wrong row perturbs by order the value itself — hundreds of
  ulp — and is caught; the unit test `test_a_structurally_wrong_row_still_fails` pins that.
- Non-finites fail regardless of budget.
- `max_ulp`, `mean_ulp`, `budget_ulp` and `rows_over_budget` are printed on **every** comparison,
  pass or fail, so drift toward the budget is visible in the artifact rather than absorbed by it.

### The residual gap, stated plainly

A tolerance cannot detect a defect smaller than the rounding floor. One key dropped from 65,536
would move the output by ~1.5e-5 relative — about 0.002 ulp — and pass any budget. The bit-exact
gate could not detect it either, because it failed unconditionally, so nothing has been lost; but
neither gate covers that case.

Closing it properly needs a **same-order reference**: run B1 with T16's `k_chunk_size` so both
sides fold identically, at which point bit-exactness becomes a meaningful question again. That is
a better experiment than any tolerance, and it is the natural follow-up.
