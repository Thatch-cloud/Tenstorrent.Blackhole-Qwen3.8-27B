# Verdict: 200 tok/s per user at 4 users and 161k is not reachable

Every number here is measured on this rig today, not assumed. The goal asked for an
honest report including evidence of unreachability, and that is what the measurements
show. Three separate lines of evidence agree, and each was found by measuring something
the programme had previously taken on faith.

## 1. The memory system is not the problem, and cannot be the solution

Run 35416870419 measured achieved DRAM bandwidth for the first time:
**405 GB/s per card, 79-80% of the 512 GB/s spec**, flat across access sizes and
consistent between read-only and read-write regimes. That is a normal sustained figure
for GDDR6 and it is the hardware limit, not a software one.

`200tps-reachability-2026-09-19.md` had assumed 85%. The real figure is worse, so every
floor moved the wrong way.

| 4 users @161k | Floor ms | Budget ms | Ceiling tok/s | |
| --- | ---: | ---: | ---: | --- |
| bf8 KV, acceptance 12.1 *(the target config)* | 81.1 | 60.5 | **149** | impossible |
| bf8 KV, acceptance 16 | 81.1 | 80.0 | 197 | impossible |
| bf4 KV, acceptance 12.1 | 67.9 | 60.5 | 178 | impossible |
| bf4 KV, acceptance 16 | 67.9 | 80.0 | 236 | feasible |

Exactly one cell reaches the target, and it needs bf4 KV *and* near-perfect T16
acceptance, against 12.1 of 16 measured. Perfect acceptance every cycle is not a
realistic operating point.

## 2. The verifier is already near the bandwidth limit where it matters

Device attribution of the T16 verifier (run 35185624322, 81 MB C++ profile, trace 24,
median of four steady replays, chip 0) totals 64.90 ms against the 66.09 ms the host
observes, so it is essentially complete:

| Component | ms | share |
| --- | ---: | ---: |
| weight-bearing (MLP gate/up + all matmuls) | 31.64 | 49% |
| GDN machinery | 20.08 | 31% |
| collectives | 3.44 | 5% |
| SDPA | 3.49 | 5% |
| everything else | 6.25 | 10% |

Weight streaming moves 9.96 GB per card in 31.64 ms, **315 GB/s, 78% of the measured
405**. There is no large inefficiency to reclaim in the dominant term.

**The optimistic bound.** If every non-weight operation vanished - the entire GDN path,
all collectives, SDPA, everything - the verifier would be 31.6 ms, the cycle 64.3 ms,
and the rate **187 tok/s per user at single-user 4096 context**. Still short of 200, at
a configuration far easier than the target. Verifier optimisation alone cannot get
there from any direction.

## 3. Speculation and concurrency are architecturally exclusive

The target needs both: speculation to commit ~12 tokens per weight pass, batching to
amortise that pass across users. They cannot currently coexist.

- **Speculation is fast-path only.** `DFlash2DraftModel` is registry metadata whose every
  method raises `DFlash2 execution requires the explicit TT combined fast runtime`. The
  plain path, which already serves 4 users at 161k, cannot speculate.
- **The fast path is single-sequence by construction**, not merely pinned. Verify rows
  are capped at 32 in four independent places, and those rows are *positions within one
  sequence*: `validate_ticket` binds them to that sequence's chunk family with causal
  masks tied to `start`. Another user's tokens cannot occupy them. `VerifierEngine` takes
  one session, `dflash_device` a scalar position, `bridge_factory` a `[1, 68]` page table
  - which is itself 68 x 64 = 4352 tokens, a fifth pin the programme's table of four
  does not list.

Making the fast path serve N users means adding a batch axis through the draft device,
verifier, masks, bridge and hook. That is weeks of architectural work, and per section 1
it still lands at 149 tok/s in the target configuration.

## What is actually reachable

| Configuration | today | plausible with work |
| --- | ---: | ---: |
| 1 user, 4096 ctx | 123 tok/s | up to ~187, needs most of the GDN path gone |
| 4 users, 161k, bf8 | not servable with speculation | ceiling 149, needs the batch-axis rewrite |
| 4 users, 161k, bf4 | not servable with speculation | ceiling 178, also needs bf4 KV qualified |

**Nothing in this table reaches 200 tok/s per user at 4 users and 161k.**

## Recommendation

1. **Re-scope the per-user target to 150 tok/s at 4 users and 161k**, or hold 200 tok/s
   and drop to one or two users at shorter context. Both are defensible; the current
   combination is not.
2. **Qualify bf4 KV.** It is required for bandwidth at 4 users, not only for capacity at
   8, and it is on the path to every surviving configuration.
3. **Measure acceptance at 161k.** It multiplies the budget linearly and 12.1 was only
   ever measured at 4096. It is the cheapest remaining experiment and the largest single
   unknown.
4. **Treat the GDN recurrence as the optimisation target if verifier work continues** -
   197 us per layer over 48 layers, the most expensive single operation - while knowing
   it buys at most the 187 tok/s bound above.
5. **Do not start the batch-axis rewrite** until 1-3 are settled. It is the largest item
   in the programme and its ceiling is already known to be below target.

## What was delivered along the way

- Lever N M1, resumable prefill, gated byte-identical on hardware (run 35416319586).
  It does not affect decode rate - its own design says the decode path is untouched -
  but it is correct and done.
- First measurement of achieved DRAM bandwidth on this rig.
- First complete device attribution of the T16 verifier, recovered from four CI runs
  that had been recorded as failures.
