# tp4/kv-nvme-1: an NVMe cold tier for the prefix state

Status: **built and tested on CPU, never run on a card, default off.** Branched from `tp4/next-1` (`758264ac`, the ship-5 production stack). With none of the `QWEN_PREFIX_NVME*` names set the
host tier, the checkpoint store and the scheduler graft behave exactly as they did (a pinned digest of twelve random-traffic runs holds that, `test_qwen_kv_nvme.FlagOffTests`).

Every effect in this note that is not a CPU measurement is labelled **ESTIMATE**; nothing of it has run on a card or on the target drive.

Revision 2 (owner decisions of 2026-10-21 ~04:00Z and a new fact about the drive): TTL since last use stays; **write-through is the default** and a finished session is queued for the drive at once; a **graceful stop drains** the writer queue; **a deploy does not clear the tier** (the fingerprint no longer holds the image build or the profile name: it holds a by-hand `KV_EPOCH`, section 3); the tier **survives the drive vanishing at run time** (section 5). Sections 12 and 13 carry the new gates and the answers.

## 0. Owner decisions (2026-10-21) this build follows

1. **Retention is for all tenants, for now.** No tenant allowlist. Keys still carry the tenant's cache salt (vLLM's chained block hash), so one tenant's blocks can never be named by another. **TTL 1 day** (`QWEN_PREFIX_NVME_TTL_S`, default 86,400), counted from the last use. (The first ask was 7 days; the owner cut it to one day once the capacity table in section 8 showed a 1 TB drive holds about 2.3 days at the stated load.)
2. **Seats are released at the end of a turn** (a separate change); the tiers are what keep a session's KV warm. So spilling to the NVMe has to be reliable when a session's KV leaves the card or the host tier, and **write-through is the default** (`QWEN_PREFIX_NVME_SPILL=through`; `evict` is the explicit alternative, section 5): "copy idle sessions to drive straight away" (owner, ~04:00Z) is `QWEN_PREFIX_NVME_THROUGH_IDLE_S=0`, a finished request's blocks queued for the drive at its next scheduler step. Its write rate is in section 8.
3. **A zero-retention node must not run the tier by accident.** The tier refuses to start (a loud line and a counter; the engine serves without it) when the process sees a zero-retention signal, unless an explicit override says otherwise, and it always needs an explicit retention acknowledgement. Section 9.
4. **TTL from the last use** (owner, ~04:00Z, "ttl from last use, scope both options"): as built, default 86,400 s; `QWEN_PREFIX_NVME_MAX_AGE_S` stays the optional absolute cap (the second option). Answered (section 13, question 1).
5. **A deploy must not clear the warm cache** (owner, ~04:00Z). The stored KV outlives an image build and a profile rename; what invalidates it is a change in what the bytes mean, tracked by hand (`KV_EPOCH`), plus the model, the drafter and the KV layout. Section 3. A graceful stop also drains the writer queue first (section 5).
6. **The whole drive may be formatted by a gate** (owner, later the same day; the namespace layout is not known to the owner, it is a 1 TB drive). Section 12, question 8.

## 1. What it is

The host KV tier (32 GiB at the ship setting) holds the attention-KV blocks vLLM evicted from the device pool; the checkpoint store (16 GiB) holds the GDN checkpoints that make a hit exact. Both are RAM and
both die with the engine process. The NVMe tier is a third level under them on a **raw namespace** (no filesystem, no md, no LVM, no dm: the later peer-to-peer path needs plain namespace LBAs):

```
 device pool (cards) --evict--> host KV tier (RAM, 32 GiB) --evict--> NVMe tier (raw namespace, ~1 TB)
        ^                              ^   (slab slot retained until written)           |
        |   existing restore           |                                                |
        +--- (TierHooks.load/advance) -+<--- read into slab slots (backend 'host') -----+
 checkpoint store (RAM, 16 GiB) --budget eviction / with its boundary block--> NVMe tier   (adopted back by the trim)
```

* **Spill on host-tier eviction, asynchronously.** `TierStore.remove(evicted=True)` calls the NVMe tier's sink (`NvmeTier.offer`) on the scheduler thread. The sink only enqueues: it keeps the record's **slab slot** (the slab is mapped with spare slots for exactly this) and the writer thread hashes, writes and journals the batch, then gives the slot back. No copy, no wait for the drive. A full queue (`QWEN_PREFIX_NVME_QUEUE_BYTES`) drops the record, as the host tier always did (`nvme_spill_dropped_queue`). A record no checkpoint reaches is not written (`nvme_spill_dropped_useless`), one already on the drive is not written twice (`nvme_spill_known`).
* **Checkpoints go with their sessions.** A GDN checkpoint is written (packed on the writer thread: header, token ids, the tensors, the drafter window it carries) when the store evicts it for its byte budget, and when the KV record of its boundary block leaves the host tier. A block of the same chain is *not* "dead" while its checkpoint is queued (`queued_ckpt`): the tail of a session leaves first, and the head must not be judged useless because the writer is a few milliseconds behind.
* **Restore on a miss in both host stores.** `effective_hit` counts the host tier's consecutive blocks *and* the NVMe's; a checkpoint missing from the store is read back and filed as its own (`PrefixRegistry.adopt`; the trim then checks its token ids like any other). The NVMe-resident blocks of a restore are read into **host-tier records** (backend `host`: NVMe -> slab slot, digest-checked on the reader threads), after which the restore is the existing code, unchanged, with every digest it already checks. In the sliced restore the NVMe blocks are read a slice at a time (`fill`), inside the slice's time budget.
* **Never worse than a miss.** A block that is gone, expired, fails its digest, has no room, or a device that errors is a miss and the turn prefills cold (the model verifies it against the cold chain in every test). Three device errors in a row latch the NVMe level off (`nvme_latched`); the host tier goes on without it. A drive that is *gone* (its controller disabled, its namespace reading 0 bytes) latches at once, with one line: section 5, "The drive vanishing".
* **Restart.** The index is a snapshot plus a journal on the drive; a new process opens the device, replays, drops entries of another layout fingerprint, and restores what was spilled. A graceful stop (a deploy) first drains the writer queue and closes the store (section 5, "The graceful stop"), and with write-through on by default only the last seconds of a session can be missing from the drive. A deploy of another image build or a renamed profile finds the tier warm (section 3).

Code: `scripts/ci/qwen_nvme_store.py` (the store), `scripts/ci/qwen_kv_nvme.py` (flags, fingerprint, codec, backends, the tier), hooks in `qwen_prefix_registry.py` and `qwen_prefix_scheduler_patch.py` (docstring item j), `serving_c2_contract.py` (names, gate, waiver), `prefix_markers.py`, `qwen_prefix_metrics.py`. `nvme_store_bench.py` is a micro-benchmark of the store for the target drive.

## 2. The store (`qwen_nvme_store`)

```
 [0, 4 KiB) [4 KiB, 8 KiB)   two superblock slots: magic, generation, geometry, the active snapshot slot, the journal epoch, crc32
 snapshot slot 0 | slot 1     the whole index; written to the slot that is not active, then the superblock flips to it
 journal                      records since the snapshot: PUT (96 entries a record), DEL, DEL_TENANT, WIPE, TOUCH; each (epoch, seq, crc32)
 data region (from a MiB)     the objects, 4 KiB-aligned extents from a coalescing first-fit allocator (rebuilt from the index at open)
```

* **O_DIRECT, aligned.** Every device access is a whole number of 4 KiB blocks at an aligned offset, enforced for a plain file too (so the CPU tests find the bug a raw namespace would). A block is 2,228,224 bytes = 544 x 4,096, so a slab slot is already aligned and a run of blocks is one `preadv`; anything else bounces through an aligned scratch.
* **Crash safety.** A put is: write the data, `fdatasync`, append the journal record that names it, `fdatasync`. A delete is the other way round: the DEL record is durable before the extent is allocatable again, and an extent a reader has pinned waits for the unpin. A snapshot writes the inactive slot, syncs, then writes the superblock (generation + 1, into the slot the older generation does not occupy) and syncs. A journal group torn mid-write is cut at the first record whose crc, epoch or sequence does not check. The result after any crash: the old state, the new state, or (for a multi-record batch) a prefix of it - the blocks of a session in index order, so a shorter restorable session. `test_qwen_nvme_store.CrashTests` kills the process at **every device call** of a put, a multi-record put, a delete (with immediate reuse of the freed extents), a tenant delete, a wipe, a snapshot and a journal wrap, on a simulated disk with a volatile write cache (a random subset of the writes since the last sync, and 512-byte torn pieces of them, reach the media), and checks that the reopened store lists only entries whose bytes verify, with no overlapping extents. A mutation that drops the data sync is caught by it.
* **A put that fails.** Before the journal was touched nothing names the extents, so they are given back; once it was, a record may be on the media whatever the error says, so the extents are *not* given back until the next open rebuilds the allocator from the index (a surviving record must never name bytes something else has overwritten). The writer retries a failed batch once, then counts it; three failures in a row latch the NVMe level off.
* **Format safety.** The store writes to a device only if it carries its own superblock, or its first MiB is all zero, or `QWEN_PREFIX_NVME_FORMAT=1` says to destroy whatever is there. A device with the store's magic and no valid superblock is *corrupt*, not blank. The device is locked exclusively (`flock`) while open: two engines on one namespace would corrupt it.
* **Entries.** Kind (KV block / checkpoint), key (the host tier's block hash; the checkpoint's boundary block hash), extent, size, the tenant tag as an 8-byte blake2b (the tag itself never reaches the device), the chain (the prompt's first block hash), the index (block number / checkpoint position), created, last used, sha256 of the bytes, the layout fingerprint. About 160 bytes each.
* **TTL, age, LRU, floor.** `QWEN_PREFIX_NVME_TTL_S` (default 1 day) is counted from the last use (a restore, or a re-spill of a held block); `..._MAX_AGE_S` (default off) is an absolute cap from the write, for a retention policy that must hold whatever the use. The LRU order is the order of last use (persisted by the snapshot and by TOUCH records at most once a minute). When the tier is full a put evicts the least recently used, never a pinned entry. The free-space floor (`..._FREE_FLOOR_BYTES`, default 5% of the data region) keeps contiguous room for the allocator and over-provisioning for the drive. `..._MAX_BYTES` caps the tier below the device.
* **Deletion.** `delete_tenant` (one journal record), `wipe` (one record; the index is cleared wholesale), `drop_where` (the fingerprint sweep). Logical deletion is immediate and durable; the bytes stay on the media until they are overwritten. `QWEN_PREFIX_NVME_DISCARD=1` asks the drive to discard (TRIM) freed extents.

## 3. Keys, the layout fingerprint, integrity

* **Key.** The host tier's own: vLLM's chained block hash, which carries the tenant's `cache_salt`. Tenants never meet. The checkpoint is keyed by its boundary block's hash, in its own kind (the same hash names the KV block and the checkpoint).
* **Fingerprint** (8 bytes of a sha256 over a fixed list of components, below). An entry whose fingerprint differs is dropped at open (`nvme_fp_drops`, one line) and never restored. **A deploy does not change it**: neither the image build nor the serving profile's name is a component.
* **Digest.** sha256 of every object, taken on the writer's hash threads and checked at restore on the reader threads right after each run lands: `QWEN_PREFIX_NVME_VERIFY=sample` (the default: the first block of a restore and one in sixteen, like the host tier), `all`, `off`. A checkpoint is always checked unless `off`. A mismatch drops the entry (out of the index at once, its journal record on the writer thread), counts `nvme_digest_failures`, and the turn falls back to a cold prefill. `QWEN_PREFIX_NVME_AUDIT=1` (gate only) reads every object back after its write and compares, and forces `all`.

### The layout fingerprint: what survives a deploy, and the KV epoch

Owner decision (~04:00Z, 2026-10-21): "deploy shouldn't clear warm cache". The first build put the image's source revision and the profile's name in the fingerprint, which emptied the tier at every build. They are gone. The components are, in order: the payload layout (`packed-v1`), **`epoch`** (`qwen_kv_nvme.KV_EPOCH`), the model repo and revision (`base` when none is selected), **`drafter`** (the drafter checkpoint's id and 12-digit revision from the pinned table, `drafter_checkpoint`; the table's default when `QWEN_FAST_DRAFTER_CHECKPOINT` is unset, so naming the default is not another drafter), the tier IO's KV layout string (cache count, chips, slice bytes, dtype, page dims, GDN dtype), the block bytes, the page size (64), the chunk (2,048), the mesh (`tp<chips>`), the GDN state dtype, the checkpoint format, **`env`** (the values of the switches in `qwen_kv_nvme.FINGERPRINTED_ENV`, below) and **`compat`** (`QWEN_PREFIX_NVME_COMPAT`, the explicit override).

**What the stored bytes depend on.** Only the prefill path writes them: prompt KV blocks, GDN checkpoints at 2,048-token boundaries (the recurrent state and the conv carry), and the drafter window rows the checkpoint carries (the TARGET model's tap outputs for the last 2,048 positions; nothing the drafter computes is stored). Decode-generated KV is never published to a tier. So what must change the fingerprint is whatever changes those bytes' values or meaning.

**`KV_EPOCH` and the bump rule** (the comment at the constant says the same, and it is the thing a kernel author must see): bump it, in the same commit, whenever a change alters (a) **prefill numerics** - any computation on the prefill path that is not bit-for-bit what the old path computed: an attention, matmul, norm, activation or GDN kernel or program config (fidelity, fp32 accumulation, summation or reduction order, topology, a partition that moves a reduction), a dtype, a quantisation, a different weights file, a rounding mode; (b) the **byte meaning of anything stored**: the KV block layout or cache-tensor order, the GDN state or conv-carry layout or dtype, the checkpoint object format, the drafter window rows (which taps, their order, their alignment); (c) the drafter's state layout, if a checkpoint ever carries drafter-side state beyond today's window rows. A change *proven* bit-exact against its baseline (an audit twin, byte for byte) needs no bump. A bump drops every stored entry at the next open (a cold prefill for every returning session; the drive is reusable at once).

**The env switches.** Every env name a profile can set or the image sets by default (the 203 names of `qwen_c2_profiles.json`, the 78 `ENV` defaults of the serving Dockerfile: 266 in all) is classified in `scripts/ci/test_qwen_kv_compat.py`, from what its readers say about the path it runs on and its exactness claim, and the test **fails on a name it has not seen**: a new profile switch cannot reach a card without someone deciding. The classes:

| class | names | in the fingerprint? |
| --- | --- | --- |
| `kv` | `QWEN_SDPA_BF8` (the served KV and the prefill SDPA operands are bf8; the dtype is also in the KV layout string), `QWEN_GDN_PREFILL_MMRS` (fused out-projection + reduce-scatter in the GDN prefill: a different fp32 summation order, documented as not proven exact), `QWEN_PREFIX_CKPT_PRECONVERTED` (the checkpoint object's form: the model's device-ready host tensors or plain torch tensors) | **yes**: `FINGERPRINTED_ENV`, by value |
| (own component) | `QWEN35_GDN_STATE_BF16` (the GDN state dtype: `gdn_bf16`), `QWEN_FAST_DRAFTER_CHECKPOINT` (`drafter`) | yes, as a component |
| `exact` (15) | `QWEN_FAST_SDPA_PF`, `QWEN_FAST_SDPA_PF_FLAGS`, `QWEN_FAST_SDPA_PF_ONEQ` (the prefill SDPA chain and its one-q-chunk variant), `QWEN_FAST_GDN_PREFILL_CONV`, `QWEN_GDN_CONV_GATES`, `QWEN_GDN_NORM_GATE`, `QWEN_GDN_PACKED_QKV`, `QWEN_GDN_PROJ_DIRECT` (GDN prefill/conv fusions), `QWEN_FAST_GRID13`, `QWEN_PROJECTION_LINKS`, `QWEN_FAST_CCL_OPTIONS`, `QWEN_FAST_CCL_TOPOLOGY` (grids, links, collective options), `QWEN_FAST_TAP_WINDOW_ALIGNED`, `QWEN_PREFIX_WINDOW_CARRY` (the drafter window's construction and carry), `QWEN_FAST_PREFILL_HANDOFF` | **no**: each is qualified bit-exact against the route it replaces (audit twins compare byte for byte); if one ever stops being exact it is a numerics change and `KV_EPOCH` must be bumped |
| `tier` (10), `audit` (47), `draft` (27), `decode` (60), `sched` (48), `memory` (28), `diag` (14), `plumbing` (13) | prefix/host-tier settings; gate-only twins and cadences; the drafter and the speculative round; the decode/verify round, its collectives, commits and kernels; Lever N policy, lanes, budgets, caps; DRAM and host reservations, parking, caches; logs, traces, probes; platform plumbing and evidence tokens | **no**: nothing they compute reaches a tier |

**Checked against the live successor.** The env difference between the live ship-5 traffic profile and its ship-6 successor is three names (`QWEN_FAST_LEVERN_ADAPTIVE`, `QWEN_FAST_OCTO_WAIVER`, `QWEN_FAST_TP4_GDN_WC`), none of them fingerprinted: that deploy keeps the tier.

**The override.** `QWEN_PREFIX_NVME_COMPAT=<token>` (a short token; it replaces the earlier `QWEN_PREFIX_NVME_CODE_VERSION`) is a component of its own: any other token is a fresh tier, so a gate (or an operator after a kernel change nobody classified) forces one without touching the drive.

**The residual risk, stated plainly.** If a change alters prefill numerics and nobody bumps `KV_EPOCH` (and the change is not one of the three byte-defining switches), the tier restores KV computed by the OLD numerics. The returning session's answer then continues from the old image's state: it equals the old image's continuation, **not the new image's own cold prefill of the same prompt**. Nothing at run time can tell. Two things stand against it: the bump rule above (written where a kernel author reads it), and the **UPGRADE gate** (section 12, U1), which qualifies two images as KV-compatible by restoring A's entries under B and comparing every restored turn with B's cold twin; a mismatch there means bump `KV_EPOCH`.

## 4. The restore interface and its two backends

`qwen_kv_nvme.RestoreBackend` has two methods and a flag:

| | `host` (built) | `p2p` (stub) |
| --- | --- | --- |
| `direct` | `False` | `True` |
| `read_to_host(tier, entries, views)` | NVMe -> the slab slots the caller reserved (reader threads, merged runs, digest checks) | - |
| `restore_to_device(tier, entries, block_ids, io)` | - | NVMe -> the device blocks the pool allocated, no host copy |

`TierHooks` asks `backend.direct`: a host backend promotes the NVMe-resident blocks to host records and the existing upload writes them; a direct backend takes the NVMe-resident blocks to the device blocks the pool allocated for them (`TierHooks.load_direct`; the host-resident blocks are written as before; the sliced restore is not offered to a direct backend and falls back to the whole restore). `load_direct` is tested with an in-memory double (`test_qwen_kv_nvme.DirectBackendTests`), so the seam a P2P backend plugs into is exercised. `QWEN_PREFIX_NVME_RESTORE=p2p` is refused at start (`P2PBackend()` raises `NotBuilt`); its contract is in section 11.

## 5. Flags

The tier is off unless `QWEN_PREFIX_NVME=1`; every value is strict (plain digits, no sign, no exponent, no space); a name set without `QWEN_PREFIX_NVME=1` is refused as inert; the switch needs the host tier (`QWEN_PREFIX_HOST_TIER_GIB`), `..._DEVICE` and the acknowledgement. Parsed by `qwen_kv_nvme.parse`, refused by the engine at start (`ValueError`) and by the contract in a profile.

| Name | Default | Meaning |
| --- | --- | --- |
| `QWEN_PREFIX_NVME` | off | `1` turns the tier on |
| `QWEN_PREFIX_NVME_DEVICE` | - | the raw namespace (an absolute path); a regular file works for tests |
| `QWEN_PREFIX_NVME_RETENTION_ACK` | - | **required** `1`: the operator confirms the owner's retention decision (all tenants, up to the TTL) and that this node does not advertise zero-retention (section 9) |
| `QWEN_PREFIX_NVME_TTL_S` | 86400 | seconds since last use after which an object is gone (1 to 366 days) |
| `QWEN_PREFIX_NVME_MAX_AGE_S` | 0 (off) | absolute cap, seconds since written |
| `QWEN_PREFIX_NVME_MAX_BYTES` | 0 (all) | most bytes the tier holds (at least 1 MiB) |
| `QWEN_PREFIX_NVME_FREE_FLOOR_BYTES` | 5% of the data region | bytes of the data region never used |
| `QWEN_PREFIX_NVME_VERIFY` | `sample` | digest check at restore: `sample`, `all`, `off` |
| `QWEN_PREFIX_NVME_RESTORE` | `host` | `host`; `p2p` is refused (not built) |
| `QWEN_PREFIX_NVME_QUEUE_BYTES` | 2 GiB | bytes waiting for the writer; also the number of spare slab slots mapped (resident only while in use) |
| `QWEN_PREFIX_NVME_THREADS` | 4 | reader and hash threads |
| `QWEN_PREFIX_NVME_SPILL` | `through` | `through` (the default): a finished session is copied toward the drive straight away, and every record entering the host tier is queued. `evict`: write only on host-tier eviction (the specification's first form; an explicit choice) |
| `QWEN_PREFIX_NVME_THROUGH_BLOCKS` | 32 | `through` only: most device blocks one scheduler step copies (a device-read cap of about 13 ms a step) |
| `QWEN_PREFIX_NVME_THROUGH_IDLE_S` | 0 | `through` only: seconds a finished request must be idle before its blocks are queued; **0 = at its next scheduler step** (not off) |
| `QWEN_PREFIX_NVME_DRAIN_S` | 4 | seconds a graceful stop may spend flushing the writer queue (0 to 8; 0 arms no stop hooks); inside the platform's stop grace (about 10 s), which the engine's own shutdown shares |
| `QWEN_PREFIX_NVME_DISCARD` | 0 | `1`: TRIM freed extents |
| `QWEN_PREFIX_NVME_COMPAT` | - | a short token in the fingerprint: any token is a fresh tier (the explicit override; replaces `..._CODE_VERSION`) |
| `QWEN_PREFIX_NVME_FORMAT` | 0 | **gate only.** `1`: initialize the device whatever it holds |
| `QWEN_PREFIX_NVME_AUDIT` | 0 | **gate only.** read back every object after its write; digests `all` |
| `QWEN_PREFIX_NVME_CMD_DIR` | - | **gate only.** a directory polled for `wipe` and `tenant.<tag>` files |
| `QWEN_PREFIX_NVME_ALLOW_ON_ZERO_RETENTION` | 0 | **gate only.** start the tier although a zero-retention signal is present (section 9) |

**Contract** (`serving_c2_contract`): a profile that names any of them needs the host tier; a **traffic** profile may name `QWEN_PREFIX_NVME=1` only under an owner traffic waiver that names it (`NVME_WAIVABLE_LEVERS`), next to the host tier's own waiver; the four gate-only names stay a gate's even under the waiver (a baked zero-retention override would defeat the guard on every node the image runs on, so overriding in production is a contract change, a decision); an inherited value is dropped under a profile that does not name it. No profile names the tier yet: profiles are generated, and the gate profile twins are part of the gate work (section 12).

**Write-through** (`through`, the default). Two parts, both bounded and neither on a decode round's critical path beyond a small slice: (a) every record that enters the host tier is queued to the writer at once (it is *held* in the tier until written: never a victim, its slot kept if it is removed meanwhile); (b) at the end of a `schedule()` call, `TierHooks.copy_idle` reads up to `..._THROUGH_BLOCKS` (32, the per-step device-read cap) still-cached device blocks of requests that have been idle for `..._THROUGH_IDLE_S` (default 0) into the host tier (the device idle, nothing yet written for the step: `flush`'s own moment; blocks cached in this step, blocks no checkpoint reaches and blocks already held anywhere are skipped), and (a) queues them. A warm copy is on its way before any eviction, and a restart loses only the last seconds. **Idle 0 means at once, not off:** the request's idle clock starts at `now + 0` when it finishes (`note_idle`), and `copy_idle` at the next step takes it when `ready <= now` (`test_idle_zero_is_immediate_not_off` freezes the clock to show it). The throughput knobs only mean something in `through`, so `THROUGH_BLOCKS` / `THROUGH_IDLE_S` beside an explicit `SPILL=evict` is refused (they would be ignored). When the NVMe level is latched or stopping, nothing is copied toward it (the idle list is cleared). Cost: section 8.

### The graceful stop (the drain)

A deploy restarts the container; the owner wants the warm cache to survive it. `NvmeTier.arm_stop_hooks()` (called by the registry once the tier is open; not at all with `QWEN_PREFIX_NVME_DRAIN_S=0`) installs three hooks that all call `NvmeTier.shutdown()`:

* a **SIGTERM handler, chained**: it starts the drain clock at the signal (`begin_stop`: from then on no offers and no restores, assignments only, safe in a handler), so the writer flushes *while the engine shuts itself down*; then it calls the previous handler (the engine core's own raises `SystemExit`, which unwinds to the exit below). If the previous disposition was the default one, nothing would run at all, so the handler drains and then re-raises the signal with the default disposition. An ignored SIGTERM is left ignored;
* a **`multiprocessing` finalizer** (`Finalize(None, ..., exitpriority=100)`): an engine-core child leaves through `os._exit`, which skips `atexit`, and runs finalizers instead;
* **`atexit`**, for a plain interpreter exit.

`shutdown(budget)` stops taking offers, lets the writer flush the queue for what is left of the budget (`QWEN_PREFIX_NVME_DRAIN_S`, default 4 s, from the first notice), drops what the writer did not reach (a few records of the last seconds; the host tier always lost them), journals the TTL clocks, **snapshots the index when the remaining budget covers it** (1 s plus about 4 microseconds an entry: ~2.7 s for 430 sessions; otherwise the journal is enough and the next open replays it) and closes the device. It returns by the budget: a writer stuck in a device call is abandoned, not waited for (the device is consistent at every journal record). It is idempotent and a forked child does nothing (it must never write the parent's drive). **Budget against the platform's grace:** the platform stops a serving container with SIGTERM and, after about 10 s, SIGKILL; the serving runtime's own shutdown shares those 10 s, which is why the default is 4 s and the first hook is the signal handler. Whether the engine's shutdown leaves the drain its 4 s is measured by gate N5 (section 12), not assumed. CPU tests: `StopTests` (flush, budget kept with a deliberately slow writer, snapshot only when time remains, no offers once stopping, idempotence, the forked-child guard, the hook chain with a fake `signal` module) and `StopProcessTests` (a real process takes a real SIGTERM, with the default disposition and with the engine-core pattern: a `multiprocessing` child whose previous handler raises `SystemExit`; afterwards the device is opened by a fresh store and every queued block is on it. With the hooks off the same tests fail.)

### The drive vanishing at run time

On 2026-10-21 the card-reset step rescanned the PCI bus. The switch's bridge windows had no room left ("can't assign; no space"), so the cache drive came back with its first BAR unassigned and the kernel disabled it ("BAR 0 not claimed", "disabling device after reset failure"). Its controller state read `dead` and its namespace 0 bytes; it was not a hardware fault. The tier now handles that, at any moment, as a degradation to the host tier, never a crash or a stall:

* **How it notices.** (1) The failing IO itself: a device call that fails with an errno only a vanished device returns (`ENODEV`, `ENXIO`, `ESHUTDOWN`, `ENOMEDIUM`) or with a `DeviceGone`; (2) after any other IO failure (`EIO` is ambiguous: a bad sector or a dead controller), and every 2 seconds from the scheduler thread's `poll()`, `qwen_nvme_store.device_problem`: a `stat` of the node, then its sysfs entries, found **by device number** (`/sys/dev/block/<major>:<minor>`, so a node that is called anything inside the container is still found) - the block device must still have a sysfs entry, its size must read non-zero and at least what the store was formatted for, and its controller's `state` (the namespace's `device/state`, and the `nvme<N>` directory above it) must not be `dead` or `deleting`. It never issues IO to the device, so a dead controller cannot hang the probe; the transient states (`resetting`, `connecting`) are not a verdict. A host without a block-device sysfs cannot be asked and is not blamed.
* **What it does.** Latches the tier off at once, with **one** log line (`nvme tier DEVICE LOST: <why>: latched off, the host tier serves without it until a restart finds the device live`) and the counter `nvme_device_lost` = 1 (`nvme_latched` = 1, `nvme_on` = 0). A write that fails with a gone-errno is not retried. The queued records are dropped and their slab slots and holds given back; the idle-copy list is cleared; no further NVMe log line is written however long the drive stays gone. A restore that was reading the drive falls back to a cold prefill like any miss (the model verifies it against the cold chain in the tests).
* **What it never does.** It never waits on the drive from the scheduler thread (the lookups, pins and touches take the in-memory lock only; the device IO is under the writer's own lock), it never formats a device that reads 0 bytes (the store refuses it as `DeviceGone` whatever `..._FORMAT` says; the registry logs `nvme tier UNAVAILABLE ... reads 0 bytes`), and the writer thread cannot die quietly (an unexpected exception latches the tier and returns the slots).
* **Deletion on a lost drive.** A wipe or a tenant delete that cannot reach the drive is reported `NOT APPLIED` (one line) and returns 0 rather than raising: the entries stay on the drive until a restart finds it live and the deletion is **repeated**. An operator who needs a deletion to hold must check for that line.
* **Coming back.** Nothing is retried in the same process (a drive that came back with a new controller is a new device to the kernel). A restart opens the tier again if the device is live: the data on the drive was untouched, and `test_the_tier_is_back_after_a_restart_once_the_device_is_live` restores a session after one.
* **Limit.** A read already in flight on a controller that hangs without failing is bounded by the kernel's NVMe IO timeout (30 s by default), not by this code: a dead controller fails IO at once, a hung one does not. Section 13 lists the lasting fix for the rescan (reserve bridge memory at boot).

CPU tests: `DriveLossTests` (the health look between steps; a gone-errno write latches with no retry; an `EIO` is a strike unless the probe explains it; read and checkpoint-read failures; deletion not applied; back after a restart; a 0-byte namespace at start is unavailable and never formatted; the writer thread), `DeviceProbeTests` (the sysfs reading, with a fake sysfs tree).

## 8. Capacity, endurance and effects (ESTIMATE unless it says CPU)

Sizes (measured on the cards, `docs/prefix-store-hygiene.md`): a KV block is 2,228,224 bytes = 34,816 B per token. A 254k-token session is 3,841 blocks = 8.56 GB; the average production prompt (~59k tokens) is ~920 blocks = 2.05 GB; a checkpoint is ~107 MB (+ up to ~105 MB of carried drafter window). An average session image on the drive is ~2.2 GB.

**Capacity of a 1 TB namespace.** Metadata is 2 snapshot slots (device/2,048 = 488 MB each) + a journal (device/4,096 = 244 MB) + 8 KiB: 1.2 GB (0.12%). With the 5% floor about 950 GB of objects: **~430 average sessions** (~370,000 index entries, ~190 MB of host RAM for the index: ESTIMATE ~500 B per entry in CPython objects).

**At a 7-day TTL retention was capacity-bound; at the 1-day TTL it is TTL-bound.** At the specification's spill rate of ~416 GB/day (~190 average sessions a day):

| spill rate (GB/day) | 100 | 136 | 200 | 416 | 800 |
| --- | --- | --- | --- | --- | --- |
| retention of the least recently used session (days) = min(7, 950 / rate) | 7 (9.5) | 7.0 | 4.7 | **2.3** | 1.2 |
| the same at the 1-day TTL = min(1, 950 / rate) | 1 | 1 | 1 | **1** | 1 |

To hold 7 days at 416 GB/day the namespace must be ~3.1 TB. With the 1-day TTL (owner, 2026-10-21) a 1 TB namespace holds the full TTL up to ~950 GB/day, about 2.3 times the stated load, so the TTL, not the LRU, decides the retention.

**Endurance.** 416 GB/day is ~152 TB a year. A 600 TBW consumer-class 1 TB drive: ~3.9 years; an enterprise 1 DWPD / 5 year drive (1,825 TBW): ~12 years. Write amplification inside the drive should stay near 1 to 1.3 (large sequential writes, whole-extent frees, 5% free floor, optional TRIM): 152 to 198 TB a year. Journal and snapshot writes are negligible (~30 MB/day of journal; a ~60 MB snapshot every few days).

**Write-through costs (the default).** `evict` (the explicit alternative) writes a block when the host tier evicts it and the drive does not hold it; `through` writes every published block of every idle session once (blocks of a follow-up turn that the drive holds are not written again, so a conversation costs its new tokens). The specification's 416 GB/day is the volume of sessions leaving the cards; `evict` writes at most that and less when a session returns from host RAM first, `through` writes all of it plus the checkpoints (+5 to 10%): **~420 to 460 GB/day** at the stated load, i.e. the same endurance row as above, never more than ~10% above it. The device-read cost is on the scheduler thread: 32 blocks a step is ~13 ms at the 5.6 GB/s the host tier measured for a full-tier spill (T3), for as many steps as the backlog needs: ~29 steps for an average session, ~120 for a 254k one; against a decode round of ~150 ms that is a slowdown of the rounds that carry a slice by under 10%, and it never exceeds `QWEN_PREFIX_NVME_THROUGH_BLOCKS`. The Lever N decode-gap floor (8 s) is unaffected unless the step budget is raised by hand.

**Restore time (host backend).** The drive was measured at 6.9 GB/s sequential into host RAM at a Gen4 x4 link; the host tier's own restore to the device ran 8.9 GB/s (T3). Sequential (not yet pipelined): 59k ~0.30 + 0.25 = **~0.55 s**; 128k ~0.64 + 0.50 = **~1.1 s**; 254k ~1.24 + 0.96 = **~2.2 s**, against a cold re-prefill of 75 to 145 s (35 to 65 times). With `verify=all` the digests run on 4 reader threads at ~6 GB/s (1.5 GB/s each), about the drive's rate. The first token of a returning 254k turn: T3's host-tier return was 6.49 s (device-resident hit 4.65 s), so **~7.7 s** from the NVMe.

**Decode stalls.** *Spill:* the scheduler thread's cost is the sink: **2.5 microseconds a record on the CPU (mean over 143 offers on a busy host; p99 25 us; measured, no payload copy)**, ~1.3 ms for a 512-record flush; the writer thread does the rest. A burst larger than the queue is dropped, not waited for. *Restore, whole, in the trim:* the NVMe read adds to the host tier's restore inside one scheduler step: `docs/prefix-store-hygiene.md` estimates the longest wait of a whole restore at 254k at ~6.5 s (T3's returning first token, 6.49 s), so ~7.7 s with the NVMe read, **0.3 s under the 8 s floor**. Run the NVMe arms **sliced** (`QWEN_PREFIX_TIER_RESTORE_SLICE`): the host tier's sliced estimate is ~5 s, and the read is spread over ~12 slices of about 0.1 s. This is the one number in this note that looks too close to leave to the whole-restore path.

**Checkpoint adoption.** A returning session whose checkpoint the store lost reads it back on the scheduler thread, once, in the trim (or in `start` of a sliced restore): the read is ~107 to 215 MB (16 to 32 ms at 6.9 GB/s), the digest ~70 to 140 ms at 1.5 GB/s, and the model's own conversion of the 96 tensors ~60 ms (measured at capture), so **~0.1 to 0.25 s** (ESTIMATE) of one scheduler step per returning session, not per block.

**Host RAM.** The writer queue (KV blocks and checkpoints together) is bounded by `QWEN_PREFIX_NVME_QUEUE_BYTES` (2 GiB): that many bytes of spare slab slots are mapped beyond the host tier's 48 GiB, resident only while records are in flight (peak +2 GiB, the checkpoints in the queue being objects the store already dropped), plus ~190 MB of index and one transient checkpoint buffer (107 to 215 MB). The 48 GiB budget the owner approved does not include these (open question 3).

**Open time.** Reading and parsing a ~60 MB snapshot of ~370,000 entries and replaying a journal: ~1 s (ESTIMATE; the first thing `nvme_store_bench.py` should time on the real drive). The fingerprint sweep and a first TTL sweep follow on the writer thread.

## 9. Retention, privacy, and the zero-retention conflict

**What is kept.** The drive holds KV derived from tenants' prompts (and the GDN state at 2,048-token boundaries, and drafter window rows): data that can in principle be turned back into text. It is plaintext on the media unless encrypted (below). Keys carry the tenant's salt; the tenant tag is stored as an 8-byte hash; no salt, tag or token is logged or exported.

**Policy (owner decision 2026-10-21).** All tenants. TTL 1 day since the last use (first 7 days, cut to 1 day for capacity). There is no allowlist. An absolute cap (`..._MAX_AGE_S`) exists, off, for a policy that must bound the age of the data whatever its use (question 1: TTL since last use is the answer; the cap is the second option, in scope). A tenant's data can be deleted by `NvmeTier.delete_salt(salt)` / `delete_tenant(tag)` (one durable journal record; admin thread) or a `tenant.<tag>` file in the command directory (gate only), the whole tier by `NvmeTier.wipe()` (also what a `reset_prefix_cache`, the prefix kill switch and the host tier's kill switch do). Deletion is logical and immediate; the bytes remain on the media until overwritten. `QWEN_PREFIX_NVME_DISCARD=1` issues TRIM, which the drive may honour late or not at all. Strong erasure is a crypto-erase or a full secure-erase of the namespace.

**The conflict.** A node whose agent holds an attestation key advertises `zero_retention` as a node label, gates no-retention work onto itself, and signs a teardown confirmation each time it destroys an inference container: *nothing survived*. A tier that keeps KV on a drive for days after the container is gone makes that statement false for any node it runs on.

**The guard.** The serving process **cannot know** what its node agent advertises: the label and the signature belong to the agent, which tells its containers nothing today (and must never put its key in one). So there are two layers:

1. **Signals the process can see** (`zero_retention_signals`): the agent's attestation key variable present in the process (a conflict by itself); `THATCH_ZERO_RETENTION=1` (the name proposed for the node agent to forward into the serving containers of an attesting node - **not set by anything today**); `THATCH_NO_LOG=1` (the container runs under the zero-retention log control); a `zero-retention` marker file in the kill-switch directory. Any of them present and `QWEN_PREFIX_NVME_ALLOW_ON_ZERO_RETENTION` not `1`: the tier does not start, logs `nvme tier REFUSED to start on a zero-retention node: <signals>`, `nvme_refused_zero_retention` = 1 and `nvme_on` = 0 are exported, no byte of the drive is touched, no slab slot is mapped for it, and the engine serves with the host tier alone. With the override the tier starts and says so.
2. **A required acknowledgement**, because layer 1 is best effort: `QWEN_PREFIX_NVME_RETENTION_ACK=1` must be in every profile that names the tier (the contract refuses the profile otherwise, the engine refuses to start otherwise). It records that the operator and the profile's waiver accept retention for all tenants for up to the TTL and that the image is only placed on nodes that do not advertise zero-retention. **Placement is the platform's control, not this process's.** The follow-ups that close the gap are the platform's: the node agent forwards `THATCH_ZERO_RETENTION=1` to the serving containers of an attesting node, and the teardown attestation either excludes nodes that run the tier or lists it.

The override is a gate's own name: a traffic profile cannot carry it, and an inherited value is dropped (`apply_environment`). A drive that is missing, not the store's, or in use does not stop the engine: `nvme tier UNAVAILABLE`, `nvme_unavailable` = 1, the host tier serves.

**Encryption at rest.** Not built; the options:

| | drive self-encryption (Opal, one locked range per namespace) | software AES on the host path |
| --- | --- | --- |
| host CPU | none | AES-XTS/GCM at the drive's rate: ~2 to 4 cores for 6.9 GB/s (ESTIMATE) on the reader and writer threads |
| P2P (NVMe -> card) | **works**: the drive decrypts, the card receives plaintext | **cannot work**: the host never touches the bytes |
| per-tenant crypto-shred | no (one key per range) | yes, with a key per tenant |
| erase | revoke the key: the whole namespace | per tenant by dropping its key |
| integrity | the digest still applies on the host path | encrypt-then-MAC |

The recommendation is Opal for the namespace (it keeps the P2P path possible and costs nothing); per-tenant crypto-shred needs software keys and gives up P2P. This is the owner's decision (open question 2). **Scoping of the two options is being done separately, on its own branch: see `docs/tp4-kv-nvme-encryption.md` (not part of this branch).** The store's object layout (`write_buffers`, `read_run`) is the one place a software cipher would sit.

## 10. What it does not do

* A session in host RAM at the moment of a restart is lost in `evict` mode (an explicit choice now), and a session only on the device pool is lost in both modes until it is copied (`through`, the default, copies a finished session at its next scheduler step); a hard kill (SIGKILL, power) loses what the writer had not written, and the device stays consistent. A block evicted from the host tier is for a few milliseconds to seconds *in flight* (queued, not yet on the drive): a request for it in that window is a miss.
* A restore reads the host-tier-missing blocks, then the existing code uploads them: the two are sequential (a pipelined slice would overlap them: not built).
* It adds no new device op and changes no card path. The checkpoint codec reads the model's preconverted tensors with `ttnn.to_torch` and converts them back with the model's own `_qwen_prefix_preconvert` (the capture's call on the same values): exact in theory, **never run on a card**; the gate's exactness arm is its check.
* The host RAM tier's slab, the checkpoint store and the registry keep their sizes and policies; no NVMe knob changes them.
* **Merging with `tp4/upload-1`** (threaded tier IO, parallel digest checks): both branches start from `tp4/next-1` and both edit `PrefixRegistry.attach_tier_io`, `TierHooks.load` and `advance`, so the merge has textual conflicts and no semantic one: the NVMe tier takes whatever IO the registry holds (the codec and the fingerprint look through a wrapper's `.io`), its promotion runs before the digest loop the upload levers parallelise, and neither touches the other's counters.

## 11. The peer-to-peer follow-up (NVMe -> card, no host bounce)

Proven on 2026-10-21, outside this repository: a read from the namespace into a card's BAR4 window through the patched kernel driver at 6.95 GB/s, byte-exact. A usable window is about 3 GiB per card at a 1 GiB offset (the top of a 4 GiB window failed its self-test). What `RestoreBackend` with `direct = True` (`P2PBackend`) needs, as written in its docstring:

* **A staging window per card**, at most 3 GiB at the 1 GiB offset: one fill moves `floor(3 GiB / block_bytes)` = 1,445 blocks; a 254k session is three to four fills.
* **Alignment.** Every object is a whole number of 4 KiB blocks at a 4 KiB-aligned LBA, and the block is 544 pages, so a run of blocks is one aligned read; the window offset and every chunk stay 4 KiB-aligned.
* **A device-side scatter op**, e.g. `ttnn.qwen_scatter_blocks_from_window(cache_tensors, window, block_ids, block_bytes, slice_bytes)`: for each block in the window, copy its `[cache tensor][chip][slice]` pieces to the page range of `block_ids[i]` in every cache tensor on every chip (the inverse of `qwen_write_blocks_raw` without the host buffer). A chip's piece of a block is 17,408 bytes = 4.25 pages, so it is not page-aligned inside the block: either the scatter distributes the whole block to all four chips over the fabric, or a later layout version (chip-major, page-padded) rewrites the cache - a new `layout` in the fingerprint, which drops the old entries cleanly.
* **Integrity without the host.** The bytes never visit host RAM, so the sha256 cannot run on them: a device-side checksum over the window compared with a CRC stored beside the digest, or the drive's end-to-end protection information. Until one exists a P2P restore verifies nothing, and `QWEN_PREFIX_NVME_VERIFY` must say so.
* **Encryption** only at the drive (Opal).
* The same sliced hold the host path has, and the same fall back to a miss.

On the host side nothing else moves: `TierHooks.load_direct` is the call site, the entries are pinned for the length of the call, and the miss paths are tested.

## 13. Questions for the owner: answered and open

1. **TTL since last use, or an absolute age?** ANSWERED (owner, 2026-10-21 ~04:00Z: "ttl from last use, scope both options"). Since the last use, as built, **1 day** (`QWEN_PREFIX_NVME_TTL_S` = 86,400): a session used daily lives as long as it is used. The absolute cap `..._MAX_AGE_S` stays an optional second knob, off by default; set it (for example 86,400) if the policy becomes "no prompt-derived data on a drive older than a day".
2. **Encryption at rest:** Opal for the namespace now (keeps P2P possible, no per-tenant shred) or software keys (per-tenant shred, no P2P)? **OPEN, not this branch's:** a separate agent scopes both options on its own branch; its write-up is `docs/tp4-kv-nvme-encryption.md`. Section 9 has only the summary table.
3. **Host RAM:** the queue's 2 GiB and the index (~190 MB) are outside the 48 GiB budget. Accept, or shrink `QWEN_PREFIX_NVME_QUEUE_BYTES`? OPEN.
4. **`through` in production?** ANSWERED (owner, ~04:00Z: "copy idle sessions to drive straight away"): write-through is the **default**, idle 0, with the per-step device-read cap (32 blocks) kept. Its write cost is in section 8 (~420 to 460 GB/day at the stated load, the same endurance row as `evict`, never more than ~10% above it). `QWEN_PREFIX_NVME_SPILL=evict` remains an explicit choice.
5. **Capacity.** ANSWERED 2026-10-21: TTL 1 day, which a 1 TB namespace holds at up to ~950 GB/day. 7 days would need ~3.1 TB.
6. **The fingerprint and deploys.** ANSWERED (owner, ~04:00Z: "deploy shouldn't clear warm cache"): the image build and the profile name are not in the fingerprint; `KV_EPOCH` (bumped by hand when prefill numerics or the stored bytes' meaning change), the model, the drafter, the KV layout and three byte-defining switches are (section 3). Deploy survival also needs the graceful stop's drain (section 5): a stop that is SIGKILLed before the drain ends loses only the last seconds. The residual risk is stated in section 3 and covered by gate U1.
7. **Zero-retention placement.** The guard and the acknowledgement are in; the node agent forwarding `THATCH_ZERO_RETENTION=1` and the teardown attestation's wording are the platform's work. OPEN.
8. **Gate prerequisites** (section 12): who writes the runner's device mapping and the plan wiring? The namespace is ANSWERED: the whole drive's single namespace may be formatted; identify it by model and serial through `/dev/disk/by-id`, never by `nvmeN`; today it holds only P2P test patterns, which the tier's `auto` format reads as not blank, so a gate needs the gate-only force-format once. STILL OPEN: the runner's device mapping and the plan wiring.
9. **The lasting fix for the PCI-rescan loss of the drive (OPEN, platform/host work).** A card reset's rescan re-enumerated the devices behind the shared switch, found its bridge windows full, and left the drive without BAR 0 (the kernel then disabled it). The tier survives that now (section 5) and gate step R1 brings the drive back by removing its function and rescanning only its own port, but every card window would need R1. The fix is to **reserve bridge memory at boot**: `pci=realloc` (so the kernel re-assigns bridge windows on a rescan) or a hotplug memory reserve on the switch's downstream ports (`pci=hpmemsize=...`), tested together with the **Gen4 retrain unit at the next reboot** (the two change PCI enumeration and should be qualified as one reboot). Until then R1 is a hard prerequisite of every tier gate that follows a card reset.
10. **The platform's stop grace.** The drain budget (4 s) assumes the platform keeps stopping a serving container with SIGTERM followed by SIGKILL after about 10 s, and that the serving runtime's own shutdown leaves the 4 s; gate N5 measures it. If it does not fit: a longer grace for serving containers, or a lower `QWEN_PREFIX_NVME_DRAIN_S`. OPEN until N5 has run.
