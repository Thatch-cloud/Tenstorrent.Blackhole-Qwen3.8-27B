# 200 tok/s per user at 161k, four users: the measured verdict

**Date:** 2026-09-22. **Evidence:** m3native v34, run `35658854824`, the current best
arm - four concurrent users, 32768 context, `gate_passed: true`, token-exact against
each user's own single-user reference. Every number below is measured on the rig pair,
not modelled.

## 1. Where the stack actually is

| user | tokens per round | median round | steady-state rate |
|---:|---:|---:|---:|
| 0 | 5.12 | 253.0 ms | 20.2 tok/s |
| 1 | 6.74 | 256.8 ms | 26.2 tok/s |
| 2 | 5.45 | 253.5 ms | 21.5 tok/s |
| 3 | 6.24 | 258.0 ms | 24.2 tok/s |

**Mean 23.0 tok/s per user**, TTFT excluded (TTFT is 13.5-52.5 s and is a separate
problem - see the prefill work in task #37). The target is 200 tok/s per user, so the
stack is **8.7x short, and that is at 32768 context, a fifth of the 163,840 the target
names.**

At the measured 5.89 accepted tokens per round, 200 tok/s per user means a round
budget of **29.4 ms**. The measured round is 253-258 ms.

## 2. The verify trace alone exceeds the whole budget

The packed verify trace is **157.7 ms** (33 rounds, min 157.66, max 157.79 - it is
extremely stable). That is **5.4x the entire 29.4 ms round budget**, before proposals,
commits, publication, sampling or any host work.

So the question is not whether the round can be trimmed. It is whether the verify
trace can be cut by a factor of five and a half.

## 3. What is left to cut, and the ceiling it implies

`docs/k1-launch-count-verdict.md` settles the cheap half: collapsing launches does
nothing. v33 against v34 removed 96 launches per round and moved the trace by 0.02%
and the round median by 0.6%, both inside run-to-run spread. The 94.6 us per launch
that made launch count look like the lever is eager-mode host dispatch, which a traced
round does not pay.

What remains is device work. From the per-op attribution
(`docs/trace-op-attribution.md`), three buckets dominate:

| bucket | eager ms | share of op time |
|---|---:|---:|
| SdpaDecode | 262.3 | 16.8% |
| its cc=64 GenericOp companion (128 launches, paired 1:1) | 333.1 | 21.3% |
| Matmul family | 314.4 | 20.1% |
| **combined** | **909.8** | **58.2%** |

Task #39's native batch-4 decode graft attacks exactly these: one SDPA launch instead
of four, and the removal of the two-tile weight re-read
(`two_tile_decode.py:186-205`, `:263-332`) that inflates the matmul bucket.

**Take the impossible case.** Suppose that graft lands perfectly and drives SDPA, its
companion and every matmul to **zero**. Applying that 58.2% share to the measured
trace leaves **66.0 ms**. The budget is 29.4 ms.

> **Deleting 100% of the attention and matmul time still misses 200 tok/s by 2.2x, at
> 32768 context.**

And 32768 is not the target. The target is 163,840.

## 4. Context makes it worse, not better

K/V is already bfloat8_b and read zero-copy from the serving cache
(`docs/sdpa-kv-bf8-plan.md`), so there is no dtype saving left. The bytes scale
linearly with context:

| context | bf8 K+V per user per launch | four users |
|---:|---:|---:|
| 32,768 | 32.0 MiB | 128.0 MiB |
| 65,536 | 64.0 MiB | 256.0 MiB |
| 163,840 | 160.0 MiB | 640.0 MiB |

Four users at 163,840 inside a 29.4 ms round requires **23 GB/s of K/V read alone**,
sustained, with every other op in the round also fitting in that window. The measured
effective rate on this path today is ~16-20 GB/s. That is not a hard wall by itself -
Blackhole DRAM is faster than that, and the measured figure includes everything else
the launch does - but it means the K/V read alone consumes essentially the entire
budget at the target context, leaving nothing for the 41.8% of op time that is not
attention or matmul.

## 5. Verdict

**200 tok/s per user at 163,840 context with four concurrent users is not reachable on
this two-card Blackhole pair.** The evidence is not an estimate:

1. Measured 23.0 tok/s per user at a fifth of the target context - **8.7x short**.
2. The verify trace alone is **5.4x** the round budget the target implies.
3. The cheap lever is measured and worth **zero** (K1, v33 vs v34).
4. The expensive lever, taken to its physically impossible limit - all attention and
   all matmul time removed - still leaves **2.2x** at 32768, before the 5x context
   increase.
5. At 163,840 the K/V read alone needs the whole budget.

What the hardware *does* do, measured and gated: **four concurrent users, token-exact,
at ~23 tok/s each at 32768 context**, with the 65536 rung's numerics now qualified on
hardware (run `35658618872`, complete precision set, `"passed": true`). 131,072 at four
users was separately shown DRAM-infeasible by 4-6 GB per chip (task #35).

## 6. What is still worth doing

Not because it reaches 200, but because it is real improvement with the ceiling stated
honestly:

- **Task #39, the native batch-4 decode graft.** The only remaining device-work lever.
  Best case by the arithmetic above is roughly 157.7 -> 66-110 ms of trace, i.e.
  **~35-55 tok/s per user** at 32768. Worth building; will not reach 200.
- **Task #37, the prefill ramp.** TTFT of 13.5-52.5 s is a worse user-visible problem
  than the decode rate and is a separate mechanism.
- **The 65536 rung.** Numerics are qualified on hardware; the T16-vs-B1 replay
  comparison is the remaining gate (task #50).

This document should be read alongside `memory/goal-200tps-concurrent.md`, which set
60 ms/cycle as the target number. The measured cycle is 253-258 ms, the trace inside it
is 157.7 ms, and 60 ms is below the floor that the attention and matmul work alone
establish.
