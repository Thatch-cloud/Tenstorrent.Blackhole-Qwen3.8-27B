# Peer-to-peer restore of KV blocks from NVMe into card DRAM: tools and models

CPU-only groundwork for restoring evicted KV blocks from an NVMe drive straight into a card's DRAM (no bounce through host RAM). Nothing here is
imported by the serving engine; nothing touches a card unless `p2p_probe.py` is run as root on a host that has the patched driver
(`patches/tt-kmd-p2pmem`) loaded.

| File | What it is |
|---|---|
| `p2p_topology.py` | Read-only. For each card and drive: will the kernel allow peer-to-peer DMA between them (`BUS_ADDR` inside a switch, `THRU_HOST_BRIDGE` through the root complex, or not at all), which ports redirect it (ACS), and the boot parameter and `setpci` command that clear the redirect |
| `p2p_probe.py` | The feasibility probe. Read arm (the default): `O_DIRECT`-read a file or block-device range into the card through p2pmem, verify it through a second path, time it against the host-bounce path. Write arm (`--mode write`): the drive DMA-reads the card's DRAM through the same mapping into a scratch range, which is read back and compared; sweeps write size and queue depth, re-aims the window across the DRAM banks with a canary read after each re-aim, soaks, and reads the PCIe AER counters before and after. `--dry-run` prints the plan, `--mock` runs the whole flow on fakes |
| `kv_shard_layout.py` | The on-drive layout (one object per card, sector-aligned, header page + shards), the final-layout arithmetic, the card-side digest specification, and a max-min-fair bandwidth model of drives, cards, a switch and ACS redirect |
| `test_*.py` | CPU tests of all three (`python -B -m unittest discover -s scripts/p2p -p 'test_*.py'`; allowlisted in `qwen-integration-cpu.yml`) |

Safety properties of the probe, each tested (and each checked by mutating the code and seeing a test fail): nothing is opened under `--dry-run`; the
slice must be free (the PCI core's `p2pmem/available` equals `size`) and no other process may have the card open; the card is woken (the busy power state
the UMD sends: the DRAM PHY is asleep otherwise) before anything touches it; the 4 GiB TLB window must come up for this process and is pinned (a dma-buf
export, so a reset is refused and FREE_TLB or close cannot pull it away) or the run stops; a source with a hole, an unwritten or delayed extent is refused
before the window is configured; a pattern written through the window must read back, inside the destination; the mapping must sit at the physical
address the slice has; the destination is painted with a sentinel before every timed run so a DMA that wrote nothing cannot pass on leftovers; a run that
compared nothing (`--verify none`) is UNVERIFIED, never PASS. `--prepare` onto a block device needs `--overwrite-device`, a device that nothing mounts,
holds, swaps or arrays, and a first MiB of zeros.

Exit status of `p2p_probe.py`: 0 PASS, 1 FAIL (a difference, or below `--min-gbps`), 2 could not run, 3 UNVERIFIED. The window is mapped uncached by the
kernel once the range is p2pmem, so CPU verification is slow and the host-bounce `--baseline` is indicative only (the real host path is the UMD's DMA).

Typical use (root, the patched driver loaded with `p2pmem_devices=<this card>`, nothing serving from the card; the card's DRAM is overwritten):

    p2p_topology.py --list
    p2p_probe.py --prepare /dev/<blank spare drive> --size 4G --overwrite-device      # or a file on a spare filesystem
    p2p_probe.py --source /dev/<that drive> --size 1G --chunk 16M --threads 4 --baseline --verify sample
    p2p_probe.py --source /dev/<that drive> --size 1G --baseline-only                 # the host-bounce path alone, for CPU-time comparison

## The write arm (`--mode write`)

The other direction: the drive reads the card. An `O_DIRECT` `pwritev` whose iovecs are pieces of the p2pmem mapping makes the drive DMA-read the card's DRAM (non-posted reads of the card's BAR) and write the bytes to a **scratch range of a drive that the operator names and owns**. The CPU first puts a deterministic random pattern into the card through the TLB window; after each batch the probe paints the range with a sentinel beforehand and reads it back with `O_DIRECT` afterwards, so a write that never happened or landed wrong cannot pass. The run stops at the first difference, the first uncorrectable AER increment, a controller that is no longer live, or a canary that does not match (it does not try again to see).

What it measures and checks:

* **Sweep.** Write sizes 696,320 B (one object's share on one card), 2,785,280 B (an object over four cards) and 22,282,240 B (a sub-run of eight objects), each at queue depths 1, 4, 8, 16 and 32 (1 is the drain-bound measurement: one sub-run on its own); rate, per-write p50/p99/max, process and worker CPU. Each write is one `pwritev` of `--iov-bytes` pieces (default 696,320). Two things to read the figures with:
  * *Queue depth is batch-synchronous.* QD writes are issued together and all are waited for before the next sentinel paint and verify, so the queue drains to zero between batches. The rates understate a steady queue of the same depth.
  * *CPU is the P2W path only.* `cpu.process_seconds` is the process CPU while the `pwritev` batches run, `cpu.worker_seconds` the sum of the worker threads' own CPU in them, and `cpu.process_fraction_of_write_time` ("cores") the first divided by the write time. The sentinel paint, the read-back compare and the AER sampling are reported apart as `cpu.non_write_process_seconds`; counting them would overstate the host CPU of P2W several times over.
* **Re-aim arm** (`--reaim`). The window is re-aimed at each DRAM bank in turn (`CONFIGURE_TLB` is three posted register writes), and the CPU reads the bank's canary through the uncached mapping before any bio is issued: a non-posted read from the same requester cannot complete before the posted writes landed. Every bank holds a different canary page and a different pattern, so a stale aim shows as a wrong canary and, independently, as wrong bytes on the drive. A canary is checked for every bank before any data is written into the card. What this arm proves is that the aim is right end to end; it cannot test the *ordering* claim itself (a read overtaking the posted writes), because microseconds of syscall and Python time sit between the ioctl and the read, so a read that raced ahead would not show here.
* **Soak** (`--soak MINUTES`). Back-to-back batches for the time asked, paced to `--soak-max-gbps` (default 2) to spare the drive's endurance, every Nth cycle painted and verified, the last one always; the write-only rate is reported per 30 s bucket so a throttle shows as a falling rate. At 2 GB/s the drive is busy about a third of the time on a Gen4 x4 link: it is a lighter "sustained load" than an unpaced one (`--soak-max-gbps 0`), and the operator's OK to the pacing belongs in the runbook.
* **AER.** The counters of the card, the drive and every bridge between them and the root port (`aer_dev_*`, `aer_rootport_*` in sysfs) before the run, after every cell, and every `--aer-interval` seconds (default 0.5) between batches inside a cell and the soak, together with the NVMe controller's state; and after it. An uncorrectable increment (the non-fatal file holds the completion timeout) stops the run within that interval plus the segment in flight (a batch of writes, one 8 MiB sentinel chunk or one read-back; a batch is at most 32 writes of 22 MB, about 0.1 s at Gen4 speed), and fails it. A sample is a few dozen small sysfs reads (about 0.2 ms on the test tree; the report carries the mean measured on the rig); the report carries the number of samples, the longest gap between two (`aer.max_gap_seconds`) and the mean cost of one (`aer.mean_check_ms`). Correctable increments are reported per function. A root port's correctable total and its devices' correctable counters count the same error, so the correctable figures are not a count of distinct errors; uncorrectable detection is not affected. A system without the counters ends UNVERIFIED, not PASS.
* **Verdict.** `PASS` needs byte-exact, no uncorrectable AER, a sustained rate of at least `--min-write-gbps` (0.25; the soak's write rate, else the slowest sweep cell at queue depth 4 or more), a sub-run that drains within `--drain-ms` (50) and, with `--reaim`, a matching canary after every re-aim. The drain is the design's: 22,282,240 B divided by the rate of the queue-depth-1 cell of that size (all its writes, the first and the slowest included), `verdict.subrun_drain_ms`. The slowest single write (`subrun_drain_max_ms`) and the 99th percentile (`subrun_drain_p99_ms`) are reported beside it and are not gated on: one slow write out of hundreds is information for the operator, not the bound the scheduler is sized by. A driver that applies the gates itself (the W1 kit does, in its summary) runs the probe with `--min-write-gbps 0 --drain-ms 1e9`: a clean run that is only slow then exits 0 and the report still carries every figure, while a byte difference, an uncorrectable AER, a canary mismatch or an aborted run still ends 1 and a run that compared or measured nothing 3.
* **Card fill.** The CPU puts the patterns and canaries into the card through the window (uncached by default, `--cpu-map`), a speed nobody has measured on the rig yet; the report carries the bytes, the time and the rate (`fill_stats`) so the first run measures it.
* **Report file.** `--json-out FILE` is written by the probe, which runs as root; when it was started through `sudo` the file is handed to the invoking user (`SUDO_UID`, `SUDO_GID`) so it can be read, moved and deleted without root.

Refusals, all before the first DMA: a scratch range is always required (`--scratch-start`, `--scratch-size`; the first MiB of a drive is never written, and nothing outside the range ever is: the drive handle is fenced); a range that is not all zeros is refused unless `--i-own-this-scratch-range` is given with the range; a block device that is mounted, swapped, held or in an array, or that someone else has open (`O_EXCL`), is refused; a PCIe link at 2.5 GT/s (Gen1) anywhere between the root port and the card or the drive is refused, as is a drive below `--min-drive-gts` (16); a destination in the top 16 MiB of a 4 GiB window (not DRAM) is refused. `--max-write-gib` is a hard stop on what the run writes to the drive; `--dry-run` prints the plan and an upper bound of the writes without opening anything.

Typical use (root, the patched driver loaded with `p2pmem_devices=<this card>`, nothing serving from the card, a drive whose scratch range may be overwritten, CI and other load off the host):

    p2p_probe.py --mode write --dry-run --scratch-start 16G --scratch-size 2G
    p2p_probe.py --mode write --device N --target /dev/<the drive> --scratch-start 16G --scratch-size 2G --i-own-this-scratch-range --reaim --json-out w.json
    p2p_probe.py --mode write --device N --target /dev/<the drive> --scratch-start 16G --scratch-size 2G --i-own-this-scratch-range --no-sweep --soak 5 --json-out soak.json

The read direction at the same sizes and queue depths is the read arm: `--source /dev/<the drive> --source-offset 16G --chunk 696320 --threads QD --size N`, which also reports its CPU time (`p2p.cpu_seconds` for the process, `p2p.worker_seconds`, `p2p.busiest_worker_seconds` and `p2p.worker_cores` per reading thread, over the timed reads only). Give each cell a fixed total (about 512 MiB to 1 GiB, a whole number of `size x QD` waves): with one wave of `size x QD` bytes (2.8 MB for 696,320 x 4) thread start-up and the first read's latency dominate and the GB/s is not a throughput.
Exit status as for the read arm: 0 PASS, 1 FAIL, 2 could not run, 3 UNVERIFIED.
