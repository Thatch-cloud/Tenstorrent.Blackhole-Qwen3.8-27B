# P0.4 run plan — Card-1 core inventory and reclaimable count

Generated by the fabric-tuning-cycle workflow; audit verdict VIOLATIONS with
seven findings, corrections incorporated. The three plan-level gates are now
registered in `spec/phases.yaml` and implemented in `gates.py` with tests.

## Tool command

`core_inventory.py --config <dispatch-config>` on the rig host, once per
config variant — the current PCIe-dispatch control config, and separately the
eth-dispatch candidate descriptor config if inventoried — each invocation its
own run ID. Phase-0 measurement: no opt-in flag, no runtime change.

## Gates (in order, via gates.py; none skipped)

| Gate | Rule | Pass condition |
| --- | --- | --- |
| both_cards | all_cards_present [0, 1] | Complete logical core map for both cards under the same dispatch config; no empty/partial map |
| dispatch_config_identity | dispatch_config_identity | Config file SHA256 matches the tool-echoed hash; record which config (control vs candidate). Guards the harvesting-patch device_id cache-key reuse risk |
| by_id_resolution | by_id_resolution | By-id resolution after any reset; (1,2) cabling pair confirmed via test_system_health per-channel peers; Logical vs Physical intra-mesh degree histograms asserted equal after mesh open, before any load step; link-state artifact recorded |
| reclaimable_arithmetic | reclaimable_arithmetic | reclaimable == tensix_total − dispatch_reserved on every card |

## Rig steps

1. Sequencing: P0.4 executes only after P0.1–P0.3 have recorded decisions
   (README steps 1/5 — "concurrently in progress" is not permitted). No ABBA
   blocks here: this is a baseline, not a candidate.
2. Reset, if needed, via `~/.local/bin/tt-smi` full path from an interactive
   shell (not on the non-interactive PATH); confirm the reset happened; then
   resolve devices by-id and record the mapping.
3. Pass `TT_MESH_GRAPH_DESC_PATH` explicitly, descriptor chosen from the
   measured link count (four links → four-channel `p150_x2`), never from card
   model; assert the degree histograms before the dump.
4. Fix the dispatch config(s); record `dispatch_config_path` + SHA256 per
   invocation; capture the tool's echoed config hash as cache evidence.
5. Run the tool per config variant; capture the inventory artifact; SHA256
   everything.
6. Evaluate gates in order; generate the record with `report_gen.py` into
   `docs/`; commit whether the inventory supports or contradicts reclamation.
7. The count feeds the P0 decision gate only (jointly with P0.2 ≥ P0.1(x4)
   and P0.3 materiality); Phase 1+ starts only after that gate passes.

## Record must cite

phase_id; run_id per config variant; dispatch_config_path + SHA256 + echoed
hash; device_resolution log; cards_present; per-card tensix_total /
dispatch_reserved / reclaimable + role map for reserved cores;
inventory_artifact_sha256; host_snapshot_id; measurement_date + rig identity;
per-gate results; `records_class: baseline` with the explicit "not a
candidate; no serving-default change" line; repo_revision; container/runtime
hashes; firmware; exact command/env; rollback note ("Not applicable —
measurement-only, no runtime state changed", stated explicitly).

## Rejection conditions

- Missing card or partial core map → both_cards FAIL; never infer a count.
- Inventory under a different config, or silent descriptor-cache reuse →
  dispatch_config_identity FAIL; rerun with cache cleared/verified.
- Identity/cabling/histogram not confirmed → by_id_resolution FAIL.
- Reclaimable arithmetic inconsistent on either card → FAIL; the number must
  not feed Phase-3 planning.
- Any output changing serving defaults, or any claim that reservations were
  removed from the serving image — outright rejection (Phase-2 eth-dispatch
  changes remain opt-in candidates behind the three-stage ladder).
- Record missing run ID/SHA256 or written outside docs/ — regenerate and
  commit; a rejection is still a committed result.
