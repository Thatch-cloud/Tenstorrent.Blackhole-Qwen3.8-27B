# P0.3 run plan — Per-stage model-load timeline

Generated by the fabric-tuning-cycle workflow; audit verdict VIOLATIONS with
seven findings, all corrections incorporated.

## Tool command

`python optimisation/fabric-relay/load_timeline.py --events
<loader-events.json>` per run; instrumented `load_target_once` against the
real checkpoint on the frozen winning-control config. ≥3 clean instrumented
runs of the same binary control (single-load timelines are inadmissible); ≥9
rigour if cross-run variability exceeds the 1.0 s tolerance.

## Gates (every run, in order; a failing run is rerun, never skipped)

| Gate | Rule | Pass condition |
| --- | --- | --- |
| stages_complete | all_stages_present | All five stages [read, deserialize, convert, upload_card0, upload_card1] present with positive durations in every accepted run |
| totals_consistent | sum_matches_total | per_stage_s sums to total_s within 1.0 s; both per-card uploads present and positive; card1_upload_share computable |

## Rig steps

1. Freeze on winning-runtime-controls config; resolve devices by-id after any
   `tt-smi -r` and re-resolve **per run** (never reuse a device number across
   a reset); verify adjacency with `test_system_health` with
   `TT_MESH_GRAPH_DESC_PATH` exported (four-channel `p150_x2` descriptor,
   chosen from the measured two-cable/four-link setup); record per-channel
   peers naming the (1,2) pair.
2. After opening the mesh and **before loading any weights**, assert Logical
   and Physical intra-mesh degree histograms agree; a `{0:2}` histogram means
   stale device number or cabling fault — abort, do not load.
3. Smoke-test the instrumentation on a short checkpoint (record loader
   patch/commit SHA and event schema version).
4. Run instrumented loads ≥3 times; per run record run_id, events SHA256,
   checkpoint SHA, loader commit, host snapshot, timestamps, and confirmation
   `WEIGHT_LOAD_FABRIC_RELAY` is unset.
5. Parse each events file; evaluate gates; aggregate per-stage medians and
   the median card1_upload_share.
6. Decision: is card-1 upload a **material share** of load time — one of the
   TWO inputs to the P0→P1 gate (the other is P0.2 ≥ P0.1(x4)); decides
   nothing alone.
7. Generate the record with `report_gen.py`; commit regardless of outcome;
   every non-applicable acceptance item marked "Not applicable
   (measurement-only baseline)" — never silently omitted.
8. **Cleanup:** restore the uninstrumented `load_target_once`, verify full
   patch reversion by source digest reconciliation against the frozen
   control, document residual warnings and the rollback command.

## Record must cite

run_id; events_artifact_sha256 + path; checkpoint_sha256; loader_commit_sha;
instrumentation_version; repo_revision_sha (frozen control commit);
host_snapshot_id; device_pair (by-id, re-resolved per run); per_stage_s;
total_s and delta_s vs 1.0 s; card1_upload_share; flag_state; per-run gate
verdicts; rollback/cleanup documentation; report SHA256.

## Rejection conditions

- A required stage missing and not re-instrumentable — phase rejected as not
  measurable, not guessed.
- Stage-sum deviation >1.0 s with no clean cause after rerun.
- Fewer than three clean instrumented runs.
- Events from a non-control runtime/checkpoint layout — does not describe the
  control.
- Instrumentation perturbs the measurement (unbounded buffering, I/O
  starvation inflating the read stage) and cannot be corrected — reject
  rather than publish a biased baseline.
- A record without run IDs/SHA256s, or claiming P1 admission on its own.
